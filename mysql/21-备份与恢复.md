# 备份与恢复

> 本章说明备份为什么是数据安全的最后一道防线，并掌握 mysqldump、XtraBackup 与 binlog 三种恢复手段的用法和取舍。


## 1.为什么备份比想象的重要

很多团队在数据库上投入大量精力做索引优化、分库分表和高可用，却把备份当成“有就行”的例行公事，直到误删表、误更新或者磁盘损坏发生，才发现备份文件根本用不上。备份的价值不在于“产生过文件”，而在于“能按期恢复出正确的数据”。

先看一张故障场景与恢复手段的对照表：

|故障场景|典型表现|可用的恢复手段|能否恢复到最新状态|
|---|---|---|---|
|误删表|执行了 DROP TABLE，表和数据文件一起消失|全量备份 + binlog 重放到该语句之前|能，前提是 binlog 完整|
|误更新|UPDATE 或 DELETE 漏写 WHERE，大批行被改错|全量备份 + binlog 定位到语句前的位置|能，定位成本较高|
|磁盘损坏|实例启动失败、表空间文件损坏|物理备份（XtraBackup）整实例恢复|恢复到备份点，之后靠 binlog 补|
|升级需要回滚|新版本不兼容，要退回旧版本|升级前的全量备份|能，回到备份点|
|机房或可用区故障|整台机器不可用|异地或对象存储上的备份副本|能，取决于备份是否异地|
|主库被删库、从库仍然完好|主库数据被清空|从库提升为主库，或用从库的备份恢复|能，接近最新|
|表中部分行被改错|只有少量行受影响|单表备份，或从 binlog 反解出修正语句|能，但需要人工核对|

这张表里藏着一个规律：全量备份决定你“从哪一刻开始恢复”，binlog 决定你“能补到多近”。两者缺一，恢复目标就只能停留在上一次备份完成的那一刻。

还需要破除两个常见误解。一是“有主从就不用备份”：主从复制会同步错误操作，DROP TABLE 一样会传到从库，从库只能解决机器故障，解决不了人为误操作。二是“备份文件存在就等于备份有效”：文件没损坏、能导入、数据对得上，三者都满足才能算有效备份。

## 2.备份分类

### 2.1 逻辑备份与物理备份

逻辑备份把数据读出来重新写成 SQL 语句或其他文本格式，物理备份直接拷贝数据文件。它们的差异远不止“命令不同”，而是决定了备份能用在什么场景：

|对比项|逻辑备份|物理备份|
|---|---|---|
|备份内容|建表语句与 INSERT 语句，或其他文本格式的数据|数据文件、表空间、undo、redo 等物理文件|
|代表工具|mysqldump、SELECT ... INTO OUTFILE|XtraBackup、MySQL Enterprise Backup、文件系统快照|
|备份速度|慢，需要把数据转换成 SQL|快，主要是顺序拷贝文件|
|备份体积|通常更小，压缩后差距明显|接近数据文件大小，压缩空间有限|
|跨版本能力|强，低版本导出一般可导入高版本|弱，一般要求同大版本|
|跨平台能力|强，与操作系统和字节序无关|弱，与操作系统、文件系统、页大小相关|
|恢复粒度|库、表、行都方便，必要时能直接改 SQL|一般只能整实例，单表恢复要额外处理|
|恢复速度|慢，逐条执行 INSERT|快，文件拷回即可|
|对线上影响|读数据并生成 SQL，CPU 与 IO 都有压力|拷贝文件，IO 压力大，但锁影响小|

一句话总结选型原则：数据量不大、需要跨版本或跨平台迁移、需要按表恢复，选逻辑备份；数据量大、要求恢复快，选物理备份。

### 2.2 全量、增量与差异

按“每次备份多少数据”划分，有三类：

|类型|备份内容|每次备份量|恢复时需要|典型场景|
|---|---|---|---|---|
|全量备份|备份全部数据|最大|只需要这一份|数据量小，每日一次|
|增量备份|只备份自上次备份以来变化的数据页或日志|最小|全量加全部增量，必须按顺序|数据量大，备份窗口小|
|差异备份|备份自上次全量以来变化的数据|介于两者之间|全量加最后一份差异|希望减少恢复步骤|

需要注意，差异备份在 SQL Server 生态里很常见，而 MySQL 的官方工具链里没有“差异备份”这个开箱概念。MySQL 场景下更常见的组合是“全量 + XtraBackup 增量 + binlog 归档”，binlog 在某种意义上承担了“差异”的角色，而且能精确到事件级别。

三种组合策略的取舍如下：

- 只做全量：最简单，恢复也最直白，代价是备份窗口随数据量线性增长。
- 全量 + 增量：备份快、占用小，但恢复必须按顺序合并，任一份增量损坏都会让后续恢复失败。
- 全量 + 增量 + binlog：能做到任意时间点恢复（PITR），链路最长，也最容易在某一环缺失时失效。

## 3.mysqldump 详解

mysqldump 逻辑备份的产物是一份 SQL 文件，里面既有建表语句也有 INSERT 语句，因此它天然具备“可读、可改、可跨版本”的特点。

### 3.1 常用参数

|参数|作用|使用场景|
|---|---|---|
|`-u` / `--user`|指定连接用户名|所有场景，建议配合只读或专用备份账号|
|`-p` / `--password`|指定密码，只写 `-p` 时交互式输入|任何时候都不要把明文密码写进命令或脚本|
|`--databases`（`-B`）|后面跟一个或多个库名，导出的文件里包含 CREATE DATABASE 与 USE 语句|整库备份、需要直接恢复到同名库时|
|`--single-transaction`|在 REPEATABLE READ 下开启一致性快照事务，备份期间不锁表|InnoDB 业务库的标准做法|
|`--master-data=2`|以注释形式记录备份开始时刻的 binlog 文件名和位置|需要做 PITR，必须知道从哪个位置开始重放|
|`--flush-logs`|备份开始前切换一个新的 binlog 文件|配合 `--master-data` 让全量备份与 binlog 起点对齐|
|`--routines`（`-R`）|导出存储过程和函数|应用依赖存储过程时必须加|
|`--events`（`-E`）|导出事件调度器中的事件|库里有定时事件时使用|
|`--triggers`|导出触发器，默认开启，用 `--skip-triggers` 关闭|默认行为即可，避免漏掉触发器|
|`--set-gtid-purged`|控制是否在文件里写入 `SET @@GLOBAL.GTID_PURGED`|先在测试库恢复通常用 OFF，主从环境按需使用|
|`--no-data`（`-d`）|只导出表结构，不导出数据|建空库、比对表结构、初始化测试环境|
|`--where`（`-w`）|只导出满足条件的行|单表按时间或状态做局部备份|
|`--default-character-set`|指定备份文件的字符集|统一写 utf8mb4，避免中文乱码|

### 3.2 常用备份示例

```bash
# 1. 整库备份并压缩：-B 让文件里带上 CREATE DATABASE 与 USE，恢复时不需要先建库
mysqldump -u root -p \
    --single-transaction \
    --master-data=2 \
    --flush-logs \
    --routines --events --triggers \
    --default-character-set=utf8mb4 \
    -B tlias | gzip > ${BACKUP_DIR}/tlias_$(date +%F_%H%M).sql.gz
```

上面只写 `-p`，密码由客户端交互式询问，这样备份脚本不会把明文密码留在 shell 历史和进程列表里。

```bash
# 2. 只备份表结构，用于对比结构或初始化空库
mysqldump -u root -p --no-data --routines --events \
    --default-character-set=utf8mb4 \
    --databases tlias > ${BACKUP_DIR}/tlias_schema.sql

# 3. 只备份数据：不带 --databases，文件里没有建库语句，可以导入任意目标库
mysqldump -u root -p --no-create-info --skip-triggers \
    --single-transaction \
    --default-character-set=utf8mb4 \
    tlias emp dept job > ${BACKUP_DIR}/tlias_data.sql
```

不带 `--databases` 时，mysqldump 把第一个参数当库名、后面的都当表名，所以第 3 条命令的含义是“备份 tlias 库的 emp、dept、job 三张表”。这种文件导入时可以用 `mysql ... 任意库名 < 文件` 指定落库位置，灵活性更高；代价是文件里没有建库语句，恢复前必须保证目标库已经存在。

```bash
# 4. 只备份某张表的部分数据：--where 限定范围，注意条件里的引号要与外层区分
mysqldump -u root -p \
    --single-transaction \
    --no-create-info \
    --where="hire_date >= '2025-01-01' AND status = 1" \
    tlias emp > ${BACKUP_DIR}/emp_2025_active.sql
```

```bash
# 5. 查看备份文件里记录的 binlog 位置，这就是 PITR 的起点
head -40 ${BACKUP_DIR}/tlias_2025-03-18_0200.sql
# -- CHANGE MASTER TO MASTER_LOG_FILE='binlog.000012', MASTER_LOG_POS=196;
```

`--master-data=2` 写的是注释，导入时会被忽略，只作为人工或脚本读取的元数据；写成 `=1` 则会写成可执行的语句，导入时真的会改变从库的复制起点，除非你明确知道后果，否则用 `=2`。另外 MySQL 8.0.26 起这个参数已被 `--source-data` 取代，注释内容也从 `CHANGE MASTER` 变成 `CHANGE REPLICATION SOURCE`，脚本里匹配关键字时要按版本区分。

### 3.3 --single-transaction 的适用边界

|存储引擎|一致性做法|备份期间是否阻塞写入|
|---|---|---|
|InnoDB|`--single-transaction` 开启一致性快照|不阻塞，靠 MVCC 读到快照数据|
|MyISAM|`--lock-tables`，对非事务表默认开启|阻塞写入，直到该表备份完成|
|同一库中混用|锁级别会被提升，InnoDB 表也一起被锁|阻塞写入|

所以“加了 `--single-transaction` 就绝对不锁表”是错的。一致性快照只覆盖事务型表，MyISAM 表在这期间仍然可能被写入，最后备份文件里不同表的时刻并不一致。业务库里如果还留着 MyISAM 表，要么把它迁到 InnoDB，要么安排在低峰期用 `--lock-tables` 并接受短暂停写。另外快照只在备份开始的那一刻建立，过程中新提交的数据不会进入这份备份，这一点要和 binlog 起点对齐理解，否则 PITR 会漏掉或重复一段数据。

## 4.从逻辑备份恢复

### 4.1 恢复命令

```bash
# 方式一：不进入客户端，直接重定向导入
mysql -u root -p --default-character-set=utf8mb4 tlias < ${BACKUP_DIR}/tlias.sql

# 方式二：压缩包用 zcat 流式导入，不需要先解压出大文件
zcat ${BACKUP_DIR}/tlias_2025-03-18_0200.sql.gz | mysql -u root -p tlias

# 方式三：先进入客户端，再用 source 执行文件
mysql -u root -p --default-character-set=utf8mb4
```

进入客户端后执行：

```sql
source /opt/backup/tlias.sql;
```

### 4.2 恢复前的准备

备份文件里不带建库语句时，第一步是建库并明确字符集，否则导入会报 Unknown database，或者按服务器默认字符集建库导致中文乱码：

```sql
CREATE DATABASE IF NOT EXISTS tlias
    DEFAULT CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;
```

如果备份用了 `--databases`，文件里自带 CREATE DATABASE 与 USE 语句，不需要提前建库，但建议先看文件头，确认其中的字符集和排序规则与目标环境一致。恢复前还要确认三件事：目标库不是正在对外服务的库、备份文件本身完整、客户端字符集与文件一致。

### 4.3 大文件恢复的性能注意

|注意点|具体做法|原因|
|---|---|---|
|关闭 binlog|导入会话执行 `SET sql_log_bin = 0;`|避免导入产生海量 binlog，白占磁盘还污染复制|
|减少刷盘|临时设置 `innodb_flush_log_at_trx_commit = 2`、`sync_binlog = 0`|导入是批量写，减少 fsync 次数提速明显|
|放大报文|`mysql --max_allowed_packet=256M`|避免大 INSERT 触发 Packet too large 中断|
|关闭约束检查|备份文件本身已含 `SET unique_checks=0` 与 `foreign_key_checks=0`|减少校验开销，前提是数据本身干净|
|扩大缓冲池|临时调大 `innodb_buffer_pool_size`|减少导入过程中的随机 IO|
|观察进度|`pv ${BACKUP_DIR}/tlias.sql \| mysql -u root -p tlias`|大文件导入动辄数小时，没有进度等于盲跑|
|并行导入|把表拆成多个文件，按表并发导入|单线程逐条 INSERT 是恢复速度的瓶颈|

关闭 binlog 需要会话级的 `SESSION_VARIABLES_ADMIN` 权限，而且只在“这次导入不需要参与复制”时才这么做，否则从库会缺数据。

### 4.4 不同恢复粒度该选哪种备份

|恢复目标|选用的备份|注意点|
|---|---|---|
|整个实例|物理备份，或 `--all-databases` 逻辑备份|物理恢复要求数据目录清空|
|单个库|`mysqldump -B dbname` 的单库备份|文件自带 CREATE DATABASE 与 USE，恢复最省事|
|单张表|单表备份，或从整库备份里截取该表段落|截取时要保留建表语句，并确认没有把其他表的 INSERT 一起留下|
|部分行|单表备份配合 `--where`，或从 binlog 反解|行级恢复优先考虑 binlog|
|回到某一时刻|全量备份加 binlog 重放|见第 6 节|

## 5.XtraBackup 物理备份

mysqldump 的瓶颈在数据量：几百 GB 的库导出要几小时，恢复往往更久；物理备份直接把数据文件拷走，恢复时放回数据目录即可。因此大库的日常备份通常以 XtraBackup 为主，mysqldump 退化为表结构和小表的补充手段。

XtraBackup 备份的是数据文件与 redo 日志，两者在备份结束的那一刻并不一致，所以备份集不能直接使用，必须先 prepare。prepare 相当于让备份集自己做一次崩溃恢复：把 redo 里已提交但未落盘的改动前滚上去，把未提交事务回滚掉，整理完的备份集才是一致可用的。

|对比项|XtraBackup|mysqldump|
|---|---|---|
|备份内容|数据文件与 redo，物理格式|建表与 INSERT 语句，文本格式|
|对写入的影响|InnoDB 热备，普通 DML 不受阻塞|快照下同样不阻塞，但生成 SQL 的 CPU 开销更大|
|备份速度|快，主要是顺序拷贝文件|慢，要把数据转成 SQL|
|备份体积|接近数据文件大小|通常更小，压缩后差距更明显|
|恢复速度|快，文件拷回数据目录即可|慢，逐条执行 INSERT|
|跨版本与跨平台|弱，要求同大版本、同平台|强|
|恢复粒度|以整实例为主，单表恢复要额外处理|库、表、行都方便|
|适用场景|几百 GB 以上的业务库|中小库、迁移、单表或部分行恢复|

工具版本必须与 MySQL 大版本对应，用 2.4 去备份 8.0 实例是新手的常见错误，升级 MySQL 时备份工具要一起升级。密码不要写在命令行里，放进权限受限的配置文件（例如 `/etc/mysql/backup.cnf`，权限 600），再用 `--defaults-file` 指定。

```bash
# 1. 全量备份，--parallel 控制拷贝线程数
xtrabackup --defaults-file=/etc/mysql/backup.cnf --backup \
    --target-dir=${BACKUP_DIR}/full_2025-03-18_0200 --parallel=4

# 2. 增量备份，--incremental-basedir 指向上一次备份目录
xtrabackup --defaults-file=/etc/mysql/backup.cnf --backup \
    --target-dir=${BACKUP_DIR}/inc_2025-03-19_0200 \
    --incremental-basedir=${BACKUP_DIR}/full_2025-03-18_0200

# 3. 准备全量备份集：应用 redo，让数据文件达到一致状态
xtrabackup --prepare --target-dir=${BACKUP_DIR}/full_2025-03-18_0200

# 4. 合并增量：除最后一份外，每次合并都要加 --apply-log-only
xtrabackup --prepare --apply-log-only \
    --target-dir=${BACKUP_DIR}/full_2025-03-18_0200
xtrabackup --prepare \
    --target-dir=${BACKUP_DIR}/full_2025-03-18_0200 \
    --incremental-dir=${BACKUP_DIR}/inc_2025-03-19_0200

# 5. 恢复：先停库、清空数据目录，再拷回并修正属主
systemctl stop mysqld
xtrabackup --defaults-file=/etc/mysql/backup.cnf \
    --copy-back --target-dir=${BACKUP_DIR}/full_2025-03-18_0200
chown -R mysql:mysql /var/lib/mysql
systemctl start mysqld
```

合并顺序不能颠倒：增量必须按时间依次合并，除最后一份外都要带 `--apply-log-only`，否则中间那次 prepare 会把尚未合并完的事务回滚掉，后面的增量就白做了。恢复出来的数据只到备份点，要补到最新还得靠 binlog，也就是下一节的内容。

备份期间要尽量避开 DDL。物理备份对普通增删改是热备，但备份过程中发生的表结构变更可能让备份集不可用，因此结构变更应安排在没有备份任务的时间窗，也可以用 `--lock-ddl` 让 DDL 等待备份完成。

## 6.基于 binlog 的时间点恢复

PITR（Point-In-Time Recovery，时间点恢复）要解决的是“回到任意一刻”，而不只是回到上一次备份。思路只有两步：先用全量备份恢复到备份完成时的状态，再把从备份点开始的 binlog 事件依次重放到故障发生前一刻。

难点在“重放到哪”。如果误操作是 `DROP TABLE emp`，那么重放到这条语句之前就必须停住并跳过它，然后从它后面继续重放正常事件。重放不是把整份 binlog 倒进去了事，而是按位置精确切分。

```mermaid
flowchart LR
    A["全量备份时间点<br/>2025-03-18 02:00<br/>binlog.000012 pos=196"] --> B["binlog 归档<br/>000012 起持续归档到异地"]
    B --> C["误操作<br/>2025-03-18 10:23:41<br/>DROP TABLE emp<br/>000015 pos=8518~8842"]
    C --> D["恢复到故障前一刻<br/>重放 000012 的 196 到 000015 的 8518"]
    D --> E["跳过误操作<br/>从 8842 继续重放 000015 的剩余事件"]
    E --> F["校验数据<br/>抽查表、行数与关键业务数据"]
```

### 6.1 mysqlbinlog 常用参数

|参数|作用|注意|
|---|---|---|
|`--start-position`|从指定位置开始读取事件|定位精确，PITR 首选|
|`--stop-position`|读到指定位置为止|“停到误操作之前”靠它|
|`--start-datetime`|读取指定时间之后的事件|秒级精度，受时钟偏移影响|
|`--stop-datetime`|读取指定时间之前的事件|同上，适合先圈定范围|
|`--database`（`-d`）|只输出指定库的事件|按事件所属默认库过滤，跨库语句可能漏，需人工核对|
|`-v` 或 `-vv`|把 ROW 格式的行事件解码成可读伪 SQL|定位误操作必加，`-vv` 更详细|
|`--result-file`|把输出写到指定文件|用绝对路径，避免重定向带来的换行差异|
|`--skip-gtids`|重放时不写 GTID 信息|把 binlog 重放到另一实例时避免 GTID 冲突|

### 6.2 重放示例

```bash
# 1. 读出 PITR 起点：--master-data=2 把 binlog 位置写成了注释
head -40 ${BACKUP_DIR}/tlias_2025-03-18_0200.sql
# -- CHANGE MASTER TO MASTER_LOG_FILE='binlog.000012', MASTER_LOG_POS=196;

# 2. 先把全量备份导回，得到备份完成时的状态
zcat ${BACKUP_DIR}/tlias_2025-03-18_0200.sql.gz | mysql -u root -p tlias

# 3. 按时间段导出 binlog：先落成文件再检查，最后才导入
mysqlbinlog --start-datetime="2025-03-18 02:00:00" \
    --stop-datetime="2025-03-18 10:23:41" \
    --database=tlias \
    /var/lib/mysql/binlog.000012 /var/lib/mysql/binlog.000013 \
    --result-file=/opt/backup/replay_part1.sql

# 文件里出现 drop、truncate 就说明范围选错了，先别导入
grep -nEi 'drop|truncate' /opt/backup/replay_part1.sql
mysql -u root -p tlias < /opt/backup/replay_part1.sql
```

```bash
# 4. 按位置精确重放到误操作之前：假设误删事件的起始位置是 8518
mysqlbinlog --start-position=196 --stop-position=8518 \
    --skip-gtids -v \
    /var/lib/mysql/binlog.000012 /var/lib/mysql/binlog.000013 \
    /var/lib/mysql/binlog.000014 /var/lib/mysql/binlog.000015 \
    | mysql -u root -p tlias

# 5. 跳过那条误操作，从它的结束位置 8842 继续重放到最新
mysqlbinlog --start-position=8842 --skip-gtids \
    /var/lib/mysql/binlog.000015 | mysql -u root -p tlias
```

重放前先把范围导成文件、用 grep 确认没有破坏性语句，比直接把 mysqlbinlog 管道给 mysql 安全得多：真导错一次，损失的是整整一段数据。如果恢复出来的实例以后要重新接入复制，重放时可以用 `SET sql_log_bin = 0` 关掉本机 binlog，或者配合 `--skip-gtids` 之后重新搭建复制关系。

### 6.3 为什么位置比时间可靠

binlog 里的时间戳是事件写入时的系统时间，按时间定位因此有三个天然的坑：主库时钟偏移或做过校时，时间戳和业务以为的时间就对不上；`--start-datetime` 只精确到秒，同一秒内的多条事件无法区分，误操作前后恰好同秒就会切错；从库重放时事件时间戳来自主库，而重放节奏由从库自己决定，用时间窗口圈定的范围会整体漂移。

所以稳妥的流程是：先用 `--start-datetime`、`--stop-datetime` 大致缩小范围，再用 `mysqlbinlog -v` 找到误操作事件的起始位置与结束位置，最后用 `--start-position`、`--stop-position` 精确重放。边界上要小心，`--stop-position` 的语义按“从该位置开始的事件不会被读到”理解最稳，不同小版本在边界上的行为可能有差异，所以“停到某条语句之前”的位置务必先用 `--result-file` 导出看一眼，确认目标语句确实不在文件里。

还有两点容易被忽略：重放期间应停掉写入，否则重放和线上写入混在一起，位置就对不上了；重放完成后要重新对齐这台实例的 binlog 位置与复制关系，不要让它带着旧的位置信息直接对外服务。

## 7.备份策略与落地

备份策略不是越频繁越好，而要同时满足两个可量化的目标：RPO（Recovery Point Objective，恢复点目标）回答“最多允许丢多少数据”，RTO（Recovery Time Objective，恢复时间目标）回答“最多允许停多久”。备份频率由 RPO 决定，恢复手段与演练深度由 RTO 决定。

### 7.1 按数据量分三档

|数据量级|备份组合|频率|典型 RPO|适用场景|
|---|---|---|---|---|
|小库（几十 GB 以内）|mysqldump 全量 + binlog 归档|每日全量，binlog 持续归档|不超过 1 天，配合 binlog 可到秒级|内部系统、中小业务库|
|中等库（几十 GB 到几百 GB）|XtraBackup 每周全量 + 每日增量 + binlog|每周全量、每日增量、binlog 持续|秒级|核心交易库|
|大库（TB 级以上、分库分表）|XtraBackup 每周全量 + 每日增量 + 定期演练|按库或分片错峰轮转|秒级|订单、日志类大库|

三档的共同点是 binlog 必须完整并且单独归档：没有 binlog，前两列的组合只能恢复到备份点，PITR 无从谈起；不同点是数据量越大，越依赖物理备份来压缩备份窗口。

### 7.2 备份放在哪、怎么验证

备份不能只留在数据库那台机器上：机器损毁、磁盘损坏、误删目录都会让备份和数据一起消失，同一个机房的对象存储也扛不住机房级故障。因此至少要有一份备份在别的机器、别的可用区或对象存储上。常见的最低配置是本地保留最近 7 天的备份用于快速恢复，异地或对象存储保留更长周期用于追溯，并且备份目录权限 700、文件权限 600，与原库的账号权限隔离——不少删库事故里，备份和主库用的是同一套凭据，结果是数据被一起删掉。

只检查“文件存在、大小正常、能解压”远远不够：dump 文件可能整段缺表，XtraBackup 备份集可能根本没 prepare 成功。有效验证只有一条路，在独立的测试实例上按真实流程恢复一次，记录耗时并抽样核对行数与关键业务数据，这就是实测的 RTO。建议每季度走一次完整恢复演练、每月做一次恢复到测试库并抽样校验，只有真正计时跑过，才知道恢复一个 200 GB 的库需要 40 分钟还是 4 小时，才知道磁盘空间够不够同时放备份和恢复出来的数据。

### 7.3 定时备份脚本的要点

- crontab 固定在低峰期执行，避开发布和报表任务，多个备份串行，不要同时抢 IO。
- 每次执行写日志：开始时间、结束时间、文件大小、退出码，日志本身也要保留足够天数。
- 失败告警接到邮件或 webhook；判据不能只有退出码，还要判断文件是否为空或明显偏小。
- 保留策略按份数淘汰，例如最近 7 份日备、4 份周备、12 份月备，淘汰脚本只删自己命名规则内的文件。
- 备份落盘后计算 sha256 记录到校验文件，恢复前先核对。

```conf
# crontab：每天 02:00 执行备份，输出追加到日志，失败即告警
0 2 * * * /opt/scripts/backup_mysql.sh >> /var/log/mysql_backup.log 2>&1
```

```bash
#!/usr/bin/env bash
set -euo pipefail
ts=$(date +%F_%H%M); file="${BACKUP_DIR}/tlias_${ts}.sql.gz"

if ! mysqldump --defaults-file=/etc/mysql/backup.cnf \
        --single-transaction --master-data=2 --flush-logs \
        --routines --events --triggers \
        --default-character-set=utf8mb4 -B tlias | gzip > "${file}"; then
    alert "mysqldump failed at ${ts}"      # 告警函数：邮件或 webhook
    exit 1
fi

# 退出码为 0 也可能是空备份，大小判断不能省
[ -s "${file}" ] || { alert "backup file is empty: ${file}"; exit 1; }
find "${BACKUP_DIR}" -maxdepth 1 -name 'tlias_*.sql.gz' -mtime +30 -delete
```

淘汰策略要和恢复链对齐：全量按天保留可以放心删，增量必须整条链一起保留或一起清理，否则会出现“有增量、没有对应全量”这种看着有备份、实际恢复不了的状态。

## 8.常见坑

这些坑的共同点是：出事之前看不出问题，出事之后才发现备份根本用不上。

|坑|成因|规避做法|
|---|---|---|
|没有 `--single-transaction` 导致备份不一致|默认逐表加锁导出，备份期间其他连接仍在提交，不同表的数据停在不同时刻|InnoDB 表统一加 `--single-transaction`，把整库放进一个一致性快照；同库混有 MyISAM 表时安排在低峰期并接受短暂停写|
|备份文件与库字符集不一致出现乱码|导出或导入时客户端字符集与文件字符集不同，中文按错误编码写入|导出与导入都显式指定 `--default-character-set=utf8mb4`，恢复前核对目标库的字符集与排序规则|
|恢复顺序错误|先导入增量或 binlog 再导入全量，后面的全量把前面的结果覆盖掉|严格按“全量 → 增量按时间依次合并 → binlog 重放”执行，脚本里加顺序校验，恢复前先读文件头记录的起点|
|备份文件权限过大泄露数据|备份里含全库数据甚至明文口令，落盘时按默认 umask 生成，同机其他用户可读|备份目录 700、文件 600，用专用只读账号执行备份，落盘后校验属主与权限|
|只备份不演练|把备份当成例行任务，只检查文件存在，恢复流程从未真正跑过|每季度做一次完整恢复演练、每月恢复到测试库抽样核对，把实测 RTO 记录下来|
|binlog 被清理导致无法做时间点恢复|`binlog_expire_logs_seconds`（旧版本是 `expire_logs_days`）到点自动删除，`--flush-logs` 还在不断切换新文件|binlog 单独归档到异地，保留期覆盖“最旧可用全量备份之后”的整段时间，确认归档成功后再让它过期|
|备份期间影响线上性能|全量导出要扫全表并生成 SQL，物理备份要顺序拷贝全部数据文件，IO 与 CPU 都被占满|安排在低峰期，限制速率（`--max-rate` 或 `pv -L`），多库错峰轮转，避免与报表、DDL 撞车|
|用 `cp` 直接拷数据文件当备份|数据文件、redo、undo 在拷贝的瞬间并不一致，拷出来的备份集无法启动或恢复出错|用 XtraBackup 备份并 `--prepare`，或停库后再拷贝；不要对运行中的实例直接 `cp` 或 `rsync` 数据目录|

这些坑可以归成两类：一类让备份文件本身不可信（不一致、乱码、权限泄露、直接拷文件），一类让备份在需要时用不上（顺序错、binlog 断了、从不演练）。前者靠参数与权限就能解决，后者只能靠归档纪律和定时演练解决，而演练恰恰是最容易被跳过的一步。

## 9.总结

1. 备份的价值不在“产生过文件”，而在“能按期恢复出正确的数据”：全量备份决定从哪一刻开始恢复，binlog 决定能补到多近，两者缺一，恢复目标就只能停在上一次备份完成的那一刻。
2. 逻辑备份可读、可改、能跨版本跨平台、支持库表行级恢复，物理备份快、体积大、适合大库整实例恢复，选型按数据量与恢复要求来定。
3. 全量、增量、差异三种方式里，MySQL 的常见组合是“全量 + XtraBackup 增量 + binlog 归档”，binlog 承担了差异的角色，而且能精确到事件级别。
4. mysqldump 的标配参数是 `--single-transaction`、`--master-data=2`、`--flush-logs`、`--routines`、`--events` 与 `--default-character-set=utf8mb4`，密码只写 `-p` 或放进权限 600 的配置文件。
5. `--single-transaction` 只对事务型表生效，同库混有 MyISAM 表时锁级别会被提升；快照时刻与 binlog 起点必须对齐，否则 PITR 会漏掉或重复一段数据。
6. 恢复前先确认目标库、文件完整性与客户端字符集；大文件恢复时关 binlog、减少刷盘、放大报文并观察进度，能省下大量时间。
7. XtraBackup 备份的是数据文件加 redo，必须 `--prepare` 之后才能用；合并增量必须按时间顺序，除最后一份外都要加 `--apply-log-only`，顺序颠倒会让前面的增量白做。
8. PITR 先用时间缩小范围、再用 `mysqlbinlog -v` 找到误操作事件的首尾位置，最后按位置精确重放并跳过误操作；导出的片段先用 grep 确认没有破坏性语句再导入。
9. 备份策略由 RPO 与 RTO 两个数字决定：RPO 决定备份频率与 binlog 是否完整，RTO 决定恢复手段与演练深度。
10. 备份至少要有一份离开数据库所在的机器，目录权限 700、文件 600，并与原库账号隔离；只判断“文件存在、大小正常”不算验证，真实恢复一次才算。
11. 保留策略按份数淘汰并与恢复链对齐：增量必须整条链一起保留或一起清理，否则会出现看着有备份、实际恢复不了的状态。
12. 漏参数、乱权限、错顺序、不演练，这四件事凑齐时备份就只是心理安慰，全部做齐才谈得上数据安全的最后一道防线。
