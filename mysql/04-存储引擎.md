# 存储引擎

> 本章比较 MySQL 常见存储引擎，重点理解为什么日常业务通常选择 InnoDB。


## 1.MySQL体系结构
存储引擎就是存储数据、建立索引、更新/查询数据等技术的实现方式。存储引擎是基于表而不是基于库的，所以存储引擎也可以被称为表引擎。

- 默认存储引擎是InnoDB

## 2.相关语句

创建表时指定存储引擎

```SQL
CREATE TABLE 表名(
        ...
) ENGINE=INNODB;
```

查看当前数据库支持的存储引擎

```SQL
show engines;
```

## 3.InnoDB

InnoDB 是一种兼顾高可靠性和高性能的通用存储引擎，在 MySQL 5.5 之后，InnoDB 是默认的 MySQL 引擎。

### 3.1 特点

- DML 操作遵循 ACID 模型，支持**事务**

- **行级锁**，提高并发访问性能

- 支持**外键**约束，保证数据的完整性和正确性

### 3.2 文件

`xxx.ibd`：xxx代表表名，InnoDB 引擎的每张表都会对应这样一个表空间文件，存储该表的表结构（frm、sdi）、数据和索引。
参数：innodb_file_per_table，决定多张表共享一个表空间（OFF）还是每张表对应一个表空间（ON）

查看MySQL变量

```SQL
show variables like 'innodb_file_per_table';
```

从idb文件提取表结构数据（在cmd执行）

```PowerShell
ibd2sdi 表名.ibd
```

### 3.3 InnoDB 逻辑存储结构

InnoDB 的逻辑存储结构由大到小依次为：表空间（tablespace）、段（segment）、区（extent）、页（page）、行（row）。

|层次|含义|
|---|---|
|表空间（tablespace）|逻辑存储结构的最高层，存放表中的数据和索引|
|段（segment）|表空间由段组成，常见的有数据段、索引段、回滚段等|
|区（extent）|段由区组成，区是连续页的集合，默认由 64 个连续的页组成|
|页（page）|磁盘管理的最小单元，默认 16 KB|
|行（row）|InnoDB 面向行存储，页中存放的就是数据行|

- **页**：页是 InnoDB 磁盘管理的最小单元，默认大小为 16 KB。InnoDB 中所有内容都按页来存放，一次磁盘读写至少处理一个页，因此页大小会影响单次 IO 的数据量

- **区**：一个区默认由 64 个连续的页组成，在默认 16 KB 页大小下即 64 × 16 KB = 1 MB。为了尽可能保证页的连续性，InnoDB 每次会按区为单位从磁盘申请空间

- **段**：表空间由段组成，段按用途划分，分为数据段（B+ 树的叶子节点）、索引段（B+ 树的非叶子节点）、回滚段（存放 undo 日志）等。InnoDB 中数据即索引，索引即数据，所以一张表的索引段与数据段都存放于同一个表空间文件中

- **表空间**：分为系统表空间与独立表空间。系统表空间文件为 `ibdata1`，存放回滚段、数据字典等信息；独立表空间为每张表单独的 `表名.ibd` 文件，由参数 `innodb_file_per_table` 控制（ON：每张表一个独立表空间；OFF：所有表共享系统表空间）

InnoDB 中常见的页类型如下：

|页类型|说明|
|---|---|
|数据页（Data Page）|`FIL_PAGE_INDEX`，B+ 树的叶子节点，存放表的行记录|
|索引页（Index Page）|`FIL_PAGE_INDEX`，B+ 树的非叶子节点，存放索引记录；与数据页使用同一页类型，只是从 B+ 树所处的层级来区分|
|Undo 页（Undo Page）|`FIL_PAGE_UNDO_LOG`，存放 undo 日志记录，供事务回滚与 MVCC 读取旧版本使用|
|Undo 日志页（Undo Log Page）|与 Undo 页是同一类页（`FIL_PAGE_UNDO_LOG`），不同资料中的中文叫法不同|
|系统页（System Page）|`FIL_PAGE_TYPE_SYS`，存放 InnoDB 内部系统信息|
|事务数据页（Transaction System Page）|`FIL_PAGE_TYPE_TRX_SYS`，存放事务系统数据，如事务 ID、回滚段信息等|
|插入缓冲位图页（Insert Buffer Bitmap Page）|`FIL_PAGE_IBUF_BITMAP`，记录每个辅助索引页在插入缓冲中的可用空间|
|插入缓冲空闲列表页（Insert Buffer Free List Page）|`FIL_PAGE_IBUF_FREE_LIST`，维护插入缓冲中可用的空闲页列表|
|未压缩的二进制大对象页（Uncompressed BLOB Page）|`FIL_PAGE_TYPE_BLOB`，当行溢出时，用于存放未压缩的大字段数据|
|压缩的二进制大对象页（Compressed BLOB Page）|`FIL_PAGE_TYPE_ZBLOB`，用于存放压缩后的大字段数据|

查看当前实例的页大小：

```sql
SHOW VARIABLES LIKE 'innodb_page_size';
```

页大小还可以通过参数 `innodb_page_size` 指定为 4 KB、8 KB、16 KB（默认）、32 KB 或 64 KB，但只能在初始化实例时指定，实例创建后不能再修改。

## 4.MyISAM

MyISAM 是 MySQL 早期的默认存储引擎。

### 4.1 特点

- 不支持事务，不支持外键

- 支持表锁，不支持行锁

- 访问速度快

### 4.2 文件

- `表名.sdi`：存储表结构信息

- `表名.MYD`：存储数据

- `表名.MYI`：存储索引

## 5.Memory

Memory 引擎的表数据是存储在内存中的，受硬件问题、断电问题的影响，只能将这些表作为临时表或缓存使用。

### 5.1 特点

- 存放在内存中，速度快

- hash索引（默认）

### 5.2 文件

- `表名.sdi`：存储表结构信息

## 6.存储引擎的比较

|特点|InnoDB|MyISAM|Memory|
|---|---|---|---|
|存储限制|64TB|受文件系统限制（单表文件通常 256TB 量级）|受 `max_heap_table_size` 与 `tmp_table_size` 限制|
|事务安全|**支持**|-|-|
|锁机制|**行锁**|表锁|表锁|
|B+tree索引|支持|支持|支持|
|Hash索引|-|-|支持|
|全文索引|支持（5.6版本之后）|支持|-|
|空间使用|高|低|N/A|
|内存使用|高|低|中等|
|批量插入速度|低|高|高|
|支持外键|**支持**|-|-|

## 7.存储引擎的选择

在选择存储引擎时，应该根据应用系统的特点选择合适的存储引擎。对于复杂的应用系统，还可以根据实际情况选择多种存储引擎进行组合。

- InnoDB: 如果应用对事务的完整性有比较高的要求，在并发条件下要求数据的一致性，数据操作除了插入和查询之外，还包含很多的更新、删除操作，则 InnoDB 是比较合适的选择

- MyISAM: 如果应用是以读操作和插入操作为主，只有很少的更新和删除操作，并且对事务的完整性、并发性要求不高，那这个存储引擎是非常合适的。

- Memory: 将所有数据保存在内存中，访问速度快，通常用于临时表及缓存。Memory 的缺陷是对表的大小有限制，太大的表无法缓存在内存中，而且无法保障数据的安全性

上面这条判断要分情况看：电商里的足迹和评论是业务数据，评论还涉及插入后改计数、需要事务与崩溃恢复，这两类都应该用 InnoDB。真正适合 MyISAM 的是只追加、不需要事务、且能接受崩溃后修复的场景，例如纯日志流水或历史报表归档；Memory 适合的是可以随时重建的临时表与缓存。多数生产库的结论是：除非有明确理由，默认都用 InnoDB。

### 存储引擎选择流程

```mermaid
flowchart TD
    A[评估业务需求] --> B{需要事务和崩溃恢复?}
    B -->|是| C[优先选择 InnoDB]
    B -->|否| D{数据是否必须常驻内存?}
    D -->|是| E[评估 Memory<br/>仅适合临时数据或缓存]
    D -->|否| F{是否以读和插入为主<br/>且不要求事务?}
    F -->|是| G[评估 MyISAM]
    F -->|否| C
```

选择存储引擎时还要结合外键、锁粒度、备份恢复和运维能力；流程图只是初筛，最终应使用真实业务负载压测。
