# 分库分表

> 本章从数据量和单机瓶颈出发，认识垂直拆分、水平拆分及 Mycat 分片配置。


## 1.介绍

分库分表是指数据量增长到单库单表无法承载时，按照一定规则把数据分散到多个数据库实例、多张表中的方案。它解决的是**容量与性能**问题，代价是引入分布式的复杂度。

**单库单表的瓶颈**：单机资源是有限的，数据量增长后主要会遇到以下问题。

|瓶颈|说明|
|---|---|
|磁盘容量|单机磁盘容量有限，数据文件与备份文件持续膨胀后可能占满磁盘|
|查询变慢|单表数据量过大时 B+ 树层级变高，索引和查询的效率都会下降|
|连接数上限|单个 MySQL 实例的最大连接数 `max_connections` 有限，高并发时连接不足|
|写入压力|单实例的写能力受磁盘、锁和日志刷盘限制，写入堆积会造成响应变慢|
|运维成本|单表过大时，DDL、备份恢复和数据清理的耗时都会急剧增加|

**垂直切分**：按照业务或字段的维度拆分。

- 垂直分库：按业务模块把不同的表拆分到不同的数据库中，例如用户库、订单库、商品库，每个库可以部署到不同服务器上

- 垂直分表：把一张表中不常用的字段或占用空间大的字段拆分到单独的表中，减小单表的行长度（这也被称为“大表拆小表”）

**水平切分**：按照数据行拆分，把同一张表的数据按规则分散到多张结构相同的表中，常见的分片方式有：

- 按 id 范围分片：如 id 在 0-500 万落在节点 1，500 万-1000 万落在节点 2

- 按 hash 取模分片：如 `id % 3`，结果决定落到哪个节点

- 按时间分片：如按天、按月把日志类数据拆分到不同表中

两者的对比：

|对比项|垂直切分|水平切分|
|---|---|---|
|拆分依据|业务模块或字段|数据行|
|单表数据量|不减少|减少，分散到多张表中|
|拆分后表结构|各表结构不同|各表结构相同|
|实现难度|较低，按业务边界梳理即可|较高，需要选择分片键和分片算法|
|扩容方式|业务边界变化时可能需要重新拆分|增加节点并调整分片规则，需要迁移数据|
|适用场景|业务边界清晰、字段多或有超大字段|单表数据量大且能选出合适的分片键|
|跨节点影响|跨业务查询需要跨库|跨分片查询需要聚合，join、排序、分页更复杂|

**分库分表之后引入的新问题**：

- 分布式事务：一次业务操作写入多个库时，本地事务无法保证整体一致性，需要分布式事务方案

- 跨库 join：原本一条 SQL 完成的多表关联变成跨库查询，中间件只能有限支持，通常需要改成多次查询后在应用层组装，或使用冗余字段

- 全局唯一 ID：各分片表自增主键会重复，需要雪花算法、号段模式或数据库号段表等方案生成全局唯一 ID

- 数据迁移与扩容：新增分片节点时数据需要重新分布，迁移期间还要保证业务可读可用，成本较高

- 聚合统计：`count`、`sum`、`order by`、`limit` 等需要在中间件层对多个节点的结果做合并，分页和排序的语义与单库不同

### 3.3 分片配置

#### schema.xml

`schema.xml` 描述的是逻辑库、逻辑表与实际数据节点、数据库实例之间的映射关系，核心标签及主要属性如下：

|标签|核心属性|作用|
|---|---|---|
|`<schema>`|`name`、`checkSQLschema`、`sqlMaxLimit`|`name` 定义逻辑库名；`checkSQLschema` 为 `true` 时自动去掉 SQL 中携带的库名（默认 `false`）；`sqlMaxLimit` 决定未指定 `limit` 时列表查询最多返回多少条记录|
|`<table>`|`name`、`dataNode`、`rule`|`name` 定义逻辑表名；`dataNode` 指定该表数据分布的数据节点，多个节点用逗号分隔；`rule` 引用 `rule.xml` 中定义的分片规则，不配置 `rule` 时只在第一个 `dataNode` 上建表|
|`<dataNode>`|`name`、`dataHost`、`database`|`name` 是数据节点名；`dataHost` 引用 `<dataHost>` 的 `name`；`database` 指定该节点对应的真实数据库名|
|`<dataHost>`|`name`、`maxCon`、`minCon`、`balance`、`writeType`、`dbType`、`dbDriver`|`name` 是唯一标识；`maxCon`/`minCon` 是最大/最小连接数；`balance` 是读写分离与负载均衡策略（0-3）；`writeType` 是写操作分发方式（0：转发到第一个 `writeHost`，其不可用时切到第二个；1：随机分发到各 `writeHost`）；`dbType` 指定数据库类型；`dbDriver` 指定驱动，支持 `native` 与 `jdbc`|

标签之间是引用关系：`<schema>` 下的 `<table>` 通过 `dataNode` 指向 `<dataNode>`，`<dataNode>` 通过 `dataHost` 指向 `<dataHost>`，`<dataHost>` 内部再用 `<writeHost>`（以及可选的 `<readHost>`）描述真实的数据库实例。一个完整示例如下：

```xml
<?xml version="1.0"?>
<!DOCTYPE mycat:schema SYSTEM "schema.dtd">
<mycat:schema xmlns:mycat="http://io.mycat/">

    <!-- 逻辑库 shopping，未指定 limit 时最多返回 100 条 -->
    <schema name="shopping" checkSQLschema="true" sqlMaxLimit="100">
        <!-- 逻辑表 tb_order，数据分布在 dn1、dn2、dn3 三个节点，按 auto-sharding-long 规则分片 -->
        <table name="tb_order" dataNode="dn1,dn2,dn3" rule="auto-sharding-long"/>
    </schema>

    <!-- 三个数据节点，分别对应三台 MySQL 上的 shopping 库 -->
    <dataNode name="dn1" dataHost="host1" database="shopping"/>
    <dataNode name="dn2" dataHost="host2" database="shopping"/>
    <dataNode name="dn3" dataHost="host3" database="shopping"/>

    <!-- 数据库实例：balance=0 表示不开启读写分离 -->
    <dataHost name="host1" maxCon="100" minCon="10" balance="0"
              writeType="0" dbType="mysql" dbDriver="native">
        <heartbeat>select user()</heartbeat>
        <writeHost host="hostM1" url="192.168.200.101:3306" user="root" password="${DB_PASSWORD}"/>
    </dataHost>

    <dataHost name="host2" maxCon="100" minCon="10" balance="0"
              writeType="0" dbType="mysql" dbDriver="native">
        <heartbeat>select user()</heartbeat>
        <writeHost host="hostM2" url="192.168.200.102:3306" user="root" password="${DB_PASSWORD}"/>
    </dataHost>

    <dataHost name="host3" maxCon="100" minCon="10" balance="0"
              writeType="0" dbType="mysql" dbDriver="native">
        <heartbeat>select user()</heartbeat>
        <writeHost host="hostM3" url="192.168.200.103:3306" user="root" password="${DB_PASSWORD}"/>
    </dataHost>

</mycat:schema>
```

配置注意事项：

- `<heartbeat>` 是 Mycat 探测后端数据库可用性的心跳语句，一般使用 `select user()`

- `<schema>` 下的 `<table>` 未配置 `rule` 时，数据不会分片，表只建立在该表的第一个 `dataNode` 上

- 上面 IP、端口和密码均为占位符，实际部署时替换为真实环境的值，并把口令放在受控配置中，不要提交到代码仓库

## 4.Mycat配置

### 4.1 schema.xml

schema.xml 作为MyCat中最重要的配置文件之一 , 涵盖了MyCat的逻辑库、逻辑表、分片规则、分片节点及数据源的配置

主要包含以下三组标签：

- schema标签

- datanode标签

- datahost标签
#### schema标签

schema 标签用于定义 MyCat实例中的逻辑库 , 一个MyCat实例中, 可以有多个逻辑库 , 可以通过 schema 标签来划分不同的逻辑库。MyCat中的逻辑库的概念，等同于MySQL中的database概念 , 需要操作某个逻辑库下的表时, 也需要切换逻辑库(use xxx)。

**核心属性**：

- name：指定自定义的逻辑库库名

- checkSQLschema：在SQL语句操作时指定了数据库名称，执行时是否自动去除；true：自动去除，false：不自动去除

- sqlMaxLimit：如果未指定limit进行查询，列表查询模式查询多少条记录
table 标签定义了MyCat中逻辑库schema下的逻辑表 , 所有需要拆分的表都需要在table标签中定义 。

**核心属性**：

- name：定义逻辑表表名，在该逻辑库下唯一

- dataNode：定义逻辑表所属的dataNode，该属性需要与dataNode标签中name对应；多个dataNode逗号分隔

- rule：分片规则的名字，分片规则名字是在rule.xml中定义的

- primaryKey：逻辑表对应真实表的主键

- type：逻辑表的类型，目前逻辑表只有全局表和普通表，如果未配置，就是普通表；全局表，配置为 global
#### dataNode标签

dataNode标签中定义了MyCat中的数据节点, 也就是我们通常说的数据分片。一个dataNode标签就是一个独立的数据分片。

**核心属性**：

- name：定义数据节点名

- dataHost：数据库实例主机名称，引用自 dataHost 标签中name属性

- database：定义分片所属数据库
#### dataHost标签

该标签在MyCat逻辑库中作为底层标签存在, 直接定义了具体的数据库实例、读写分离、心跳语句。

**核心属性**：

- name：唯一标识，供上层标签使用

- maxCon/minCon：最大连接数/最小连接数

- balance：负载均衡策略，取值 0,1,2,3

- writeType：写操作分发方式（0：写操作转发到第一个writeHost，第一个挂了，切换到第二个；1：写操作随机分发到配置的writeHost）

- dbDriver：数据库驱动，支持 native、jdbc
### 4.2 rule.xml

rule.xml中定义所有拆分表的规则, 在使用过程中可以灵活的使用分片算法, 或者对同一个分片算法使用不同的参数, 它让分片过程可配 置化。

主要包含两类标签：

- tableRule

- Function
### 4.3 server.xml

`server.xml` 是 Mycat 1.x 的主要配置文件。

server.xml配置文件包含了MyCat的系统配置信息。

主要有两个重要的标签：

- system

- user

#### system标签

对应的系统配置项及其含义，参考[server系统配置信息含义](https://mcnerzykwkel.feishu.cn/sheets/JkgNsdO9Ch7H7ft8J6scJCPAnAf?from=from_copylink)：
#### user标签

`<user>` 标签定义连接 Mycat 的账号以及该账号可以访问的逻辑库。

**核心属性**：

- name：登录 Mycat 的用户名

- password：登录密码

- schemas：该用户可以访问的逻辑库，多个逻辑库用逗号分隔；配置为 `true` 表示可以访问全部逻辑库

- readOnly：该用户是否只读，`true` 表示只能执行查询；不配置该属性时默认可读写

`server.xml` 中 `<system>` 与 `<user>` 的完整配置片段（口令为占位符，实际部署时替换为真实环境的值）：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE mycat:server SYSTEM "server.dtd">
<mycat:server xmlns:mycat="http://io.mycat/">
    <system>
        <property name="serverPort">8066</property>
        <property name="managerPort">9066</property>
        <property name="defaultSqlParser">druidparser</property>
    </system>

    <!-- 应用账号：可以访问 shopping、itcast 两个逻辑库 -->
    <user name="root">
        <property name="password">${DB_PASSWORD}</property>
        <property name="schemas">shopping,itcast</property>
    </user>

    <!-- 只读账号：可以访问全部逻辑库，且只能执行查询 -->
    <user name="readonly">
        <property name="password">${DB_PASSWORD}</property>
        <property name="schemas">true</property>
        <property name="readOnly">true</property>
    </user>
</mycat:server>
```

说明：

- `<user>` 的 `name`、`password`、`schemas`、`readOnly` 既可以写成标签属性，也可以写成上面的 `<property>` 子标签，两种写法都能被 Mycat 解析

- `schemas` 中列出的逻辑库必须已经在 `schema.xml` 的 `<schema name="...">` 中定义过，否则该账号登录后无法访问这些库

- `<system>` 中的 `serverPort`、`managerPort` 分别对应数据访问端口和管理端口，与 6.2 节中提到的 8066、9066 一致
## 5.Mycat分片

### 5.1 垂直拆分

在业务系统中, 涉及以下表结构 ,但是由于用户与订单每天都会产生大量的数据, 单台服务器的数据存储及处理能力是有限的, 可以对数据 库表进行拆分, 原有的数据库表如下：
#### 5.1.1 准备

分别在三台MySQL中创建数据库 shopping。
#### 5.1.2 配置

按 id 范围分片使用 `rule.xml` 中的 `auto-sharding-long` 规则，先在 `rule.xml` 里定义规则名和它引用的算法：

```xml
<tableRule name="auto-sharding-long">
    <rule>
        <columns>id</columns>
        <algorithm>rang-long</algorithm>
    </rule>
</tableRule>

<function name="rang-long" class="io.mycat.route.function.AutoPartitionByLong">
    <property name="mapFile">autopartition-long.txt</property>
</function>
```

说明：

- `<columns>`：参与分片的字段，这里按 `id` 分片

- `<algorithm>`：引用的算法名，必须与下面 `<function name="...">` 的 `name` 一致（这里都是 `rang-long`）

- `<function>` 的 `class` 是范围分片的实现类，`mapFile` 指向保存分段区间的文件名

然后在 `schema.xml` 中把逻辑表与这条规则关联起来：

```xml
<schema name="shopping" checkSQLschema="true" sqlMaxLimit="100">
    <table name="tb_order" dataNode="dn1,dn2,dn3" rule="auto-sharding-long"/>
</schema>
```

`autopartition-long.txt` 位于 Mycat 的 conf 目录下，每行描述一个分段，格式为 `起始值-结束值=数据节点索引`：

```properties
# K=1000，M=10000
0-500M=0
500M-1000M=1
1000M-1500M=2
```

- 分段区间里的 `M` 表示 10000（`K` 表示 1000），因此 `500M` 就是 500 万，`0-500M` 表示 id 在 0 到 500 万这一段的数据落到第 0 个分片，`500M-1000M` 落到第 1 个分片，以此类推，相当于每 500 万一段

- 等号右边是数据节点的下标，从 0 开始，顺序对应 `<table>` 的 `dataNode` 属性中列出的数据节点（`dn1` 为 0、`dn2` 为 1、`dn3` 为 2）

- 分段区间要按从小到大的顺序排列，不能重叠；分段的个数不能超过 `dataNode` 的数量，否则超出范围的数据无法路由

### 5.2 水平拆分

在业务系统中, 有一张表(日志表), 业务系统每天都会产生大量的日志数据 , 单台服务器的数据存储及处理能力是有限的, 可以对数据库表 进行拆分。
#### 5.2.1 准备

分别在三台MySQL中创建数据库 itcast。
#### 5.2.2 配置

取模分片在 `rule.xml` 中的定义如下：

```xml
<tableRule name="mod-long">
    <rule>
        <columns>id</columns>
        <algorithm>mod-long</algorithm>
    </rule>
</tableRule>

<function name="mod-long" class="io.mycat.route.function.PartitionByMod">
    <property name="count">3</property>
</function>
```

然后在 `schema.xml` 中通过 `rule="mod-long"` 引用这条规则：

```xml
<schema name="itcast" checkSQLschema="true" sqlMaxLimit="100">
    <table name="tb_log" dataNode="dn1,dn2,dn3" rule="mod-long"/>
</schema>
```

**注意**：`<property name="count">` 的值表示分片数量，也就是对分片字段取模时的模数，它必须与 `<table>` 的 `dataNode` 数量保持一致。上面的表配了 3 个 dataNode，`count` 就是 3；如果改成 4，那么 `id % 4` 为 3 的数据会被路由到第 4 个分片，而实际只配置了 3 个数据节点，数据就会落到不存在的节点上，导致写入失败。同理，`count` 小于 dataNode 数量时，多出来的数据节点永远不会被写入，分片不均匀。
#### 5.2.3 测试
- 在Mycat中创建表、插入数据后分表会自动创建和插入相应的数据，不需要像垂直分表那样手动创建表

### 5.3 分片规则

#### 5.3.1 分片规则-范围

根据指定的字段及其配置的范围与数据节点的对应情况， 来决定该数据属于哪一个分片。
#### 5.3.2 分片规则-取模

根据指定的字段值与节点数量进行求模运算，根据运算结果， 来决定该数据属于哪一个分片。
- 范围分片和取模分片只适用于数字，其他如字符串就不适用了

#### 5.3.3 分片规则-一致性hash

所谓一致性哈希， 相同的哈希因子计算值总是被划分到相同的分区表中，不会因为分区节点的增加而改变原来数据的分区位置。
#### 5.3.4 分片规则-枚举

通过在配置文件中配置可能的枚举值, 指定数据分布到不同数据节点上, 本规则适用于按照身份、性别、状态拆分数据等业务 。
#### 5.3.5 分片规则-应用指定

运行阶段由应用自主决定路由到那个分片 , 直接根据字符子串（必须是数字）计算分片号。
#### 5.3.6 分片规则-固定分片hash算法

该算法类似于十进制的求模运算，但是为二进制的操作，例如，取 id 的二进制低 10 位 与 1111111111 进行位 \& 运算。
#### 5.3.7 分片规则-字符串hash解析

截取字符串中的指定位置的子字符串, 进行hash算法， 算出分片。
#### 5.3.8 分片规则-按（天）日期分片

按日期分片根据分片字段的日期与起始日期相差多少天来计算分片，常用于按天或按固定天数切分的日志、流水类表。`rule.xml` 中的定义：

```xml
<tableRule name="sharding-by-date">
    <rule>
        <columns>create_time</columns>
        <algorithm>sharding-by-date</algorithm>
    </rule>
</tableRule>

<function name="sharding-by-date" class="io.mycat.route.function.PartitionByDate">
    <property name="dateFormat">yyyy-MM-dd</property>
    <property name="sBeginDate">2022-01-01</property>
    <property name="sEndDate">2022-01-31</property>
    <property name="sPartionDay">10</property>
</function>
```

主要参数：

|参数|含义|
|---|---|
|`dateFormat`|日期格式，默认为 `yyyy-MM-dd`|
|`sBeginDate`|起始日期，格式为 `yyyy-MM-dd`|
|`sEndDate`|结束日期，可以省略；省略后按 `sPartionDay` 无限往后分片，不再有结束边界|
|`sPartionDay`|每多少天为一个分片|

上例中 `sBeginDate=2022-01-01`、`sPartionDay=10`，即从 2022-01-01 起每 10 天为一个分片：前 10 天（2022-01-01 到 2022-01-10）落在第 0 个分片，第二个 10 天（2022-01-11 到 2022-01-20）落在第 1 个分片，以此类推。

`schema.xml` 中的配置：

```xml
<schema name="shopping" checkSQLschema="true" sqlMaxLimit="100">
    <table name="tb_order" dataNode="dn1,dn2,dn3" rule="sharding-by-date"/>
</schema>
```

说明：

- 分片字段的值要能按 `dateFormat` 解析成日期，格式不匹配时无法路由

- 分片下标从 0 开始，顺序对应 `<table>` 的 `dataNode` 属性中列出的数据节点，因此 `dataNode` 的数量不能少于按规则划分出的分片数量，否则超出范围的数据无法正常路由
#### 5.3.9 分片规则-自然月

使用场景为按照月份来分片, 每个自然月为一个分片。
## 6.Mycat管理及监控

### 6.1 Mycat原理

Mycat从客户端接收到信息后，会先进行SQL语句解析，进行分片分析和路由分析，根据分片规则将 SQL 路由到相应的数据库节点，Mycat 支持读写分离，将写操作发往主库，读操作发往从库，服务器处理运行Mycat路由过来的SQL后，将运行结果返回给Mycat，Mycat从各节点获取数据后，在中间件层进行结果合并和聚合处理，如果SQL语句有排序操作和分页操作，会对聚合后的数据进行排序处理和分页处理，最后把最终结果返回给客户端。

Mycat默认开通2个端口，可以在[server.xml](https://mcnerzykwkel.feishu.cn/file/HV1Lb4yr5ojkhfxzctkcYyihnzd?from=from_copylink)中进行修改：

- 8066 数据访问端口，即进行 DML 和 DDL 操作
