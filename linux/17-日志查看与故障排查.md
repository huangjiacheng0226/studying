# 九、日志查看与故障排查

> 服务出问题时，日志是唯一不会说谎的证人：本篇讲清楚日志存在哪里、用什么命令看，以及一条从“服务没反应”查到根因的固定路线。

## 1. 学习目标与前置知识

读完本篇应能：

1. 说清 systemd 的 journal 日志与 `/var/log` 下文本日志的分工，知道常见日志文件各自记什么、该看哪个。
2. 用 `tail` 实时盯日志，用 `grep` 在日志里筛选、排除和计数，并知道大文件为什么先截取再过滤会快得多。
3. 用 `journalctl` 按服务、时间、优先级、启动次数过滤日志，会开启持久化，也会清理旧日志。
4. 按一套固定顺序排查“服务不可用”，用 `systemctl`、`ss`、`curl`、`df`、`free`、`top` 一步步缩小范围。
5. 认出六类典型故障的日志特征，并用 logrotate 防止日志把磁盘写满。

前置知识：[04-Linux基础命令](04-Linux基础命令.md) 的 tail、grep 与管道；[06-Linux实用操作-快捷键与软件服务](06-Linux实用操作-快捷键与软件服务.md) 的 systemctl；[09-Linux实用操作-网络传输与端口](09-Linux实用操作-网络传输与端口.md) 的端口与 curl；[10-Linux实用操作-进程与主机状态](10-Linux实用操作-进程与主机状态.md) 的 df、free、top；[14-文本处理三剑客](14-文本处理三剑客.md) 的 grep 与 awk。

## 2. 日志体系总览

Linux 上的日志有两条主线。一条由 systemd 的 journald 负责，把服务启动、单元状态变化、内核消息集中收进 journal；另一条由 rsyslog 负责，按“设施 + 级别”把消息分流到 `/var/log` 下的文本文件。两者经常同时在跑，同一件事在两边都查得到，区别在查询方式和保留策略。

| 对比项 | systemd 的 journal | /var/log 下的文本日志 |
| --- | --- | --- |
| 存储形式 | 二进制文件，不能直接用编辑器改 | 纯文本，任何工具都能读 |
| 默认位置 | `/run/log/journal` 在内存，`/var/log/journal` 在磁盘 | `/var/log/messages`、`/var/log/syslog` 等 |
| 查看工具 | `journalctl` | `tail`、`grep`、`less`、awk |
| 主要覆盖 | 服务启动、单元状态、内核与开机早期消息 | 应用自己写的日志、认证、定时任务 |
| 保留策略 | 默认按大小滚动，不持久化时重启即丢 | 由 logrotate 按天或按大小滚动 |
| 擅长场景 | 按服务名、时间、优先级、启动次数精确过滤 | 应用自定义格式，便于脚本批量处理 |

需要记住的分工：要查“服务为什么起不来、谁改了单元状态”，先看 journal；要查“业务请求报了什么错”，先看应用写在 `/var/log` 里的文本日志。

### 2.1 常见日志文件

| 日志文件 | 内容 | 典型问题 | 查看方式 |
| --- | --- | --- | --- |
| `/var/log/messages` | 系统通用消息，CentOS/RHEL 系主日志 | 内核报错、服务启动失败、硬件告警 | `tail -f /var/log/messages` |
| `/var/log/syslog` | 系统通用消息，Debian/Ubuntu 系主日志 | 与 messages 同类的排障入口 | `tail -f /var/log/syslog` |
| `/var/log/secure` | 认证与授权记录，CentOS/RHEL 系 | 登录爆破、sudo 失败、su 切换被拒 | `grep "Failed password" /var/log/secure` |
| `/var/log/auth.log` | 认证与授权记录，Debian/Ubuntu 系 | 与 secure 同类，只是文件名不同 | `grep "Failed password" /var/log/auth.log` |
| `/var/log/cron` | crontab 任务的执行记录 | 定时任务没执行或执行时报错 | `grep CRON /var/log/cron` |
| `/var/log/boot.log` | 开机过程与启动脚本的输出 | 开机卡住、启动脚本里某一步失败 | `less /var/log/boot.log` |
| `/var/log/dmesg` | 内核环形缓冲区的一份快照 | 磁盘 IO 错误、网卡异常、内存不足被杀进程 | `dmesg -T` |
| `/var/log/nginx/` | access.log 访问日志、error.log 错误日志 | 502、404、上游超时、连接被打满 | `tail -n 100 /var/log/nginx/error.log` |
| `/var/log/mysql/` | error.log 服务日志、slow.log 慢查询 | 连接被拒、表损坏、慢 SQL 拖垮服务 | `tail -n 100 /var/log/mysql/error.log` |

几个容易踩的点：Debian 系没有 `/var/log/messages`，查通用消息要看 `/var/log/syslog`；`/var/log/dmesg` 是开机时的一份快照，想看当前内核缓冲区得直接跑 `dmesg`；`/var/log/nginx` 与 `/var/log/mysql` 是目录，日志文件在目录里面，安装方式不同文件名可能略有差异。

### 2.2 一条日志的生命周期

应用产生的日志最终能出现在终端上，中间要经过“产生、收集、落盘、查看”四段路。

~~~mermaid
flowchart LR
    A[应用程序写日志] --> B{谁负责收集}
    B -->|systemd 托管的服务| C[journald 收进 journal]
    B -->|程序自己指定文件| D[直接写 /var/log/app 下]
    B -->|程序往 syslog 发送| E[rsyslog 按设施与级别分流]
    C --> F[journalctl 查看]
    C --> G[可转发给 rsyslog]
    E --> H["/var/log/messages、secure、cron 等"]
    D --> I[tail 与 grep 查看]
    H --> I
    F --> J[定位故障根因]
    I --> J
~~~

理解这张图有三点好处：知道程序把日志交给了谁，就知道该用哪个工具去看；systemd 托管的服务即使程序自己没写日志文件，输出也会被 journald 收走；rsyslog 之后再无额外收集者，所以 `/var/log` 里的文件默认不会被自动清理，这也是第 8 节讲 logrotate 的原因。

## 3. tail：实时查看日志

`tail` 默认打印文件末尾 10 行。日志只会在末尾追加，最新的内容永远在最后，所以 tail 是看日志的第一选择；相对的 `head` 看开头，适合确认服务启动时的头几行有没有报错。

| 写法 | 作用 | 使用时机 |
| --- | --- | --- |
| `tail app.log` | 打印末尾 10 行 | 快速看一眼最新情况 |
| `tail -n 100 app.log` | 打印末尾 100 行 | 出错后回看一小段上下文 |
| `tail -n +100 app.log` | 从第 100 行打印到末尾 | 想跳过前面已知正常的启动日志 |
| `tail -f app.log` | 先打印末尾 10 行，再持续跟踪新内容 | 边操作边看日志实时输出 |
| `tail -F app.log` | 与 -f 类似，但文件被重建后会重新打开 | 生产环境长期跟踪，日志会滚动 |
| `tail -f a.log b.log` | 同时跟踪多个文件，输出前带文件名 | 前后端或两个服务一起盯着看 |

~~~bash
tail -n 100 /var/log/nginx/error.log
tail -n 50 /var/log/app/app.log
tail -F /var/log/messages
~~~

### 3.1 -f 与 -F 的区别

`-f` 的原理是打开文件后持续读取追加的字节，它记住的是打开那一刻的文件描述符。logrotate 滚动日志时做的是“改名 + 新建”：先把 `app.log` 改名为 `app.log.1`，再要求程序新建一个空的 `app.log`。此时 `-f` 仍然盯着最初那个文件对象，也就是已被改名的 `app.log.1`，新写进 `app.log` 的内容它看不到，终端会长时间没有任何输出，很容易被误判成“服务不写日志了”。

`-F` 等价于 `--follow=name --retry`：它按文件名跟踪，发现文件被删除或重建就关掉旧句柄、重新打开同名文件，因此日志滚动后依然能看到新内容。

| 场景 | 选哪个 | 原因 |
| --- | --- | --- |
| 临时调试，日志不会滚动 | `-f` | 实现最简单，开销最小 |
| 生产环境长期跟踪 | `-F` | 日志滚动后会自动重新打开，不会静默失效 |

### 3.2 实时过滤与输出缓冲

盯着全量日志很难受，通常一边跟踪一边过滤。但放进管道后 `grep` 默认按块缓冲，要攒满一块才打印，表现就是“命令跑了，屏幕半天不动”。加 `--line-buffered` 让它每读一行就立刻输出。

~~~bash
tail -f /var/log/app/app.log | grep --line-buffered "ERROR"
tail -f /var/log/app/app.log | grep --line-buffered "关键字" | awk '{print $1, $2}'
tail -F /var/log/nginx/access.log | grep --line-buffered " 500 "
~~~

第二条命令在持续过滤的基础上再切出时间和某一列，适合盯错误集中在什么时间点；第三条盯着访问日志里的 500 响应。停止跟踪用快捷键 Ctrl + C。

## 4. grep 在日志里的常用组合

grep 的基础用法在 [14-文本处理三剑客](14-文本处理三剑客.md) 已经讲过，这里只整理日志场景下的固定套路：按级别筛、看上下文、排噪音、计数、多关键字一次命中。

| 写法 | 作用 | 日志场景 |
| --- | --- | --- |
| `grep "ERROR" app.log` | 筛出含 ERROR 的行 | 只看错误级别 |
| `grep -C 3 "ERROR" app.log` | 匹配行前后各显示 3 行 | 报错只有一行，原因在前后几行 |
| `grep -B 5 "Caused by" app.log` | 只显示匹配行之前 5 行 | 顺着异常堆栈往上找触发点 |
| `grep -A 10 "Exception" app.log` | 显示匹配行之后 10 行 | 看完整堆栈 |
| `grep -v "DEBUG" app.log` | 排除匹配的行 | 去掉刷屏的调试日志 |
| `grep -c "ERROR" app.log` | 只输出匹配行数 | 判断错误量级 |
| `grep -i "error" app.log` | 忽略大小写 | 日志里 error、Error 混着写 |
| `grep -E "ERROR\|WARN" app.log` | 一次匹配多个关键字 | 同时看两个级别 |
| `grep -n "ERROR" app.log` | 附带行号 | 便于和配置文件行号对齐 |

~~~bash
grep -c "ERROR" /var/log/app/app.log
grep -C 3 "OutOfMemoryError" /var/log/app/app.log
grep -v "DEBUG" /var/log/app/app.log | grep -c "ERROR"
grep -iE "error|exception|failed" /var/log/app/app.log | tail -n 20
grep -E "500|502|504" /var/log/nginx/access.log | awk '{print $7}' | sort | uniq -c | sort -rn
~~~

第三条组合先排掉调试日志再数错误行，得到的是“真正的错误量”；最后一条把 5xx 请求的 URL 取出来去重计数，一眼就能看出哪个接口在报错。

日志文件动辄几百兆时，直接全文件 grep 要扫完整份数据，慢且没必要。更快的做法是先缩小数据集：用 `tail` 截取最近一段再过滤，凡是“最近一次故障”的排查都应该这么写。

~~~bash
tail -n 5000 /var/log/app/app.log | grep -C 3 "ERROR"
tail -n 2000 /var/log/app/app.log | grep -c "ERROR"
sed -n '10000,12000p' /var/log/app/app.log | grep "ERROR"
~~~

这三条分别覆盖“最近 5000 行里看错误上下文”“最近 2000 行里数错误条数”“已知大致行段时只筛这一段”。如果确实需要整个文件的范围，再用 `grep` 直接扫，并考虑先用 `zgrep` 查已经压缩的旧日志。

## 5. journalctl：查看 systemd 日志

journalctl 是 systemd 日志的专用查询工具。它最大的价值是“按来源查”：每条日志都带上了服务单元名、优先级、PID、启动批次等元数据，所以能精确地问“nginx 这个单元在本次启动后报过什么错”。

| 选项 | 作用 | 典型用法 |
| --- | --- | --- |
| `-u 服务名` | 只看某个单元的日志 | `journalctl -u nginx` |
| `-f` | 实时跟踪新日志 | `journalctl -u app -f` |
| `--since` | 指定起始时间 | `journalctl --since "10 min ago"` |
| `--until` | 指定结束时间 | `journalctl --since "09:00" --until "10:00"` |
| `-p err` | 只看不低于该优先级的日志 | `journalctl -p err -b` |
| `-n 100` | 只显示最后 100 条 | `journalctl -u app -n 100` |
| `--no-pager` | 不分页，直接输出完 | 写脚本或输出重定向时必加 |
| `-b` | 只看本次开机以来的日志 | `journalctl -b -u app` |
| `-b -1` | 看上一次开机的日志 | 排查意外重启前的现场 |
| `-k` | 只看内核消息，等价于看 dmesg | `journalctl -k -p err` |
| `--disk-usage` | 查看 journal 占用的磁盘空间 | 磁盘告警时先看它 |
| `--vacuum-time=7d` | 删除 7 天前的日志归档 | 空间紧张时清理 |
| `--vacuum-size=500M` | 只保留最近 500 MB | 更精确地控制占用 |

~~~bash
journalctl -u nginx -n 50 --no-pager
journalctl -u app --since "10 min ago" --no-pager
journalctl -u app --since "2024-05-01 09:00" --until "2024-05-01 09:30"
journalctl -p err -b --no-pager
journalctl -b -1 -u app -n 100 --no-pager
journalctl -k | grep -i "out of memory"
journalctl --disk-usage
sudo journalctl --vacuum-time=7d
~~~

优先级选项 `-p` 可以写级别名，也可以写数字：

| 写法 | 含义 |
| --- | --- |
| `-p emerg` 或 `-p 0` | 系统不可用 |
| `-p alert` 或 `-p 1` | 必须立即处理 |
| `-p crit` 或 `-p 2` | 严重错误 |
| `-p err` 或 `-p 3` | 错误，排障最常用 |
| `-p warning` 或 `-p 4` | 警告 |
| `-p info` 或 `-p 6` | 普通信息 |

`-p err` 的实际含义是“该级别及以上”，所以写 `-p err` 会把 err、crit、alert、emerg 都带出来。

### 5.1 journal 的持久化

默认配置下 journal 只写在内存的 `/run/log/journal` 里，系统重启就清空。判断方法很简单：看 `/var/log/journal` 目录是否存在，不存在就说明没有持久化。

~~~bash
ls -ld /var/log/journal
sudo mkdir -p /var/log/journal
sudo systemd-tmpfiles --create --prefix /var/log/journal
sudo systemctl restart systemd-journald
journalctl --disk-usage
~~~

四步的含义是：先确认目录不存在，再手工建出目录，用 systemd-tmpfiles 按系统规则补齐属主与权限，最后重启 journald 让它改用新目录。重启后再用 `journalctl -b -1` 就能查到上一次开机的日志。持久化空间由 `/etc/systemd/journald.conf` 里的 `SystemMaxUse` 与 `MaxRetentionSec` 控制，改完同样要重启 journald。

## 6. 故障排查通用套路

“服务访问不了”是一类现象，不是一类原因。有效率的做法是沿固定顺序逐层收敛：先看进程在不在，再看端口听没听，再看本机通不通，再看远程通不通，最后才钻进日志和配置。每一步都有明确的“是/否”结论，能一次性划掉一大片可能。

~~~mermaid
flowchart TD
    A[用户反馈：服务访问不了] --> B{服务是否在跑}
    B -->|不在| B1[systemctl status 看退出码与报错]
    B -->|在| C{端口是否在监听}
    C -->|没听| C1[看应用启动日志与绑定地址]
    C -->|在听| D{本机能否访问}
    D -->|不能| D1[curl 127.0.0.1 看应用响应]
    D -->|能| E{远程能否访问}
    E -->|不能| E1[查防火墙与安全组规则]
    E -->|能| F[看应用日志与应用报错]
    F --> G[看系统日志 journalctl 与 messages]
    G --> H{资源是否充足}
    H -->|磁盘满或内存紧| H1[df -h 与 free 清理和扩容]
    H -->|资源正常| I[检查配置与权限]
    I --> J[定位根因并修复]
~~~

每一层对应的命令与结论：

| 步骤 | 命令 | 看什么 | 结论 |
| --- | --- | --- | --- |
| 服务是否在跑 | `systemctl status app` | Active 状态、退出码、最近日志 | 显示 failed 或 inactive 就是没起来 |
| 端口是否在听 | `ss -lntp` | 目标端口有没有进程监听 | 没有该端口说明应用没绑定成功 |
| 本机能否访问 | `curl -v http://127.0.0.1:8080/` | HTTP 状态码、连接是否被拒 | 本机能通说明应用本身正常 |
| 远程能否访问 | `curl -v http://${SERVER_IP}:8080/` | 是否超时或被拒 | 本机通远程不通就是网络或防火墙 |
| 看应用日志 | `tail -n 100 /var/log/app/app.log` | 业务异常、堆栈 | 直接指向代码或数据问题 |
| 看系统日志 | `journalctl -u app -n 100 --no-pager` | 启动失败原因、被信号杀死 | 能看到端口占用、权限拒绝等系统级原因 |
| 检查磁盘 | `df -h` | 各分区剩余空间 | 使用率 100% 会让日志也写不进去 |
| 检查内存 | `free -h` | 可用内存与 swap | 可用内存极低要怀疑 OOM |
| 检查负载与进程 | `top` | 负载、CPU、内存占用最高的进程 | 找异常进程或判断是否被拖垮 |
| 检查文件与权限 | `ls -l /usr/local/app/app.jar` | 属主、属组、读写执行位 | 应用用户读不到文件就会启动失败 |

两个使用要点：一是顺序不要跳，跳过去就容易在“日志没报错”上浪费时间，因为很多故障根本到不了应用层；二是每步都留下证据，把命令和输出记下来，下次同类问题可以直接对照。

## 7. 六类典型故障清单

| 现象 | 可能原因 | 排查命令 | 常见结论 |
| --- | --- | --- | --- |
| 服务起不来 | 配置文件写错、端口被占、依赖服务未启动、jar 路径错误 | `systemctl status app`、`journalctl -u app -n 100` | 单元文件 `ExecStart` 路径写错，或配置里端口冲突 |
| 端口被占用 | 旧进程没退干净、同一端口起了两个实例 | `ss -lntp`、`lsof -i:8080`、`ps -ef` | 先 `kill` 掉旧进程再启动，或改成其他端口 |
| 磁盘满导致服务异常 | 日志或上传文件把分区写满 | `df -h`、`du -sh /var/log/*`、`journalctl --disk-usage` | 清理旧日志并配置 logrotate，扩容数据盘 |
| 内存不足被 OOM 杀死 | 应用内存泄漏、堆设置过大、同机部署过多服务 | `dmesg -T`、`journalctl -k`、`free -h`、`grep -i "out of memory" /var/log/messages` | 日志里有 out of memory 就调小堆或加内存 |
| 时间不同步 | 虚拟机挂起后时钟漂移、未启用 NTP | `timedatectl`、`date`、`journalctl -u chronyd` | 证书校验失败或定时任务提前执行，开启时间同步 |
| 权限不足无法读写 | 目录属主不是应用用户、文件权限过严 | `ls -l`、`namei -l /var/log/app/app.log`、`id appuser` | 用 `chown` 把目录交给应用用户，检查父目录执行位 |

两类容易看走眼的故障值得单说。第一类是 OOM：应用日志里往往只有一行突兀的“进程结束”，真正的证据在内核日志里，必须用 `dmesg -T` 或 `journalctl -k` 才能看到 out of memory 与被杀进程名。第二类是时间不同步：现象常常是“HTTPS 请求突然全部失败”或“定时任务在错误的时刻执行”，而应用自身日志只报证书过期或时间非法，所以排障时要顺手看一眼 `timedatectl`。

## 8. 日志管理：logrotate

日志一直在写，如果没人管，某一个 `app.log` 早晚会把所在分区撑满，接着数据库写不进去、服务起不来，故障从“日志问题”升级成“整机故障”。logrotate 就是解决这件事的工具：它由 systemd 的 `logrotate.timer` 或 cron 每天触发一次，按配置把日志改名归档、压缩旧文件、删掉过期文件，并通知服务重新打开日志文件。

logrotate 的两层配置分工明确：`/etc/logrotate.conf` 是全局默认值，`/etc/logrotate.d/` 下的每个文件是某个应用自己的规则，后者会覆盖前者。系统自带的服务（nginx、mysql 等）安装时通常已经放好了自己的规则，我们可以照着它的格式给自研应用加一份。

~~~conf
# /etc/logrotate.d/app
/var/log/app/app.log {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    create 0640 appuser appuser
    dateext
    postrotate
        systemctl reload app > /dev/null 2>&1 || true
    endscript
}
~~~

逐项解释配置里的关键字：

| 配置项 | 作用 |
| --- | --- |
| `daily` | 每天滚动一次，也可写 `weekly`、`monthly` 或 `size 100M` |
| `rotate 7` | 连同当前文件最多保留 7 份，更旧的删除 |
| `compress` | 归档文件用 gzip 压缩，显著省空间 |
| `delaycompress` | 本次滚动先不压缩，留给还在写的进程一个缓冲期 |
| `missingok` | 日志文件不存在时不报错，适合日志按需生成的应用 |
| `notifempty` | 空文件不滚动，避免产生一堆空归档 |
| `create 0640 appuser appuser` | 滚动后按指定权限与属主新建空文件 |
| `dateext` | 归档名带日期后缀，例如 `app.log-20240501` |
| `postrotate ... endscript` | 滚动完成后执行的收尾命令，通常用来重载服务 |

`postrotate` 那段是整份配置里最关键的：日志文件被改名后，服务仍然通过旧的文件描述符往里写，新文件会一直是空的，文件句柄也会越来越多。执行 `systemctl reload app` 或给进程发 `kill -USR1` 让它重新打开日志文件，才能真正完成切割。很多“日志切了但新文件没内容”的问题就出在漏了这一步。

不想等到第二天验证配置，可以用 `-d` 做演练，它只打印将要执行的动作而不动文件：

~~~bash
sudo logrotate -d /etc/logrotate.d/app
sudo logrotate -vf /etc/logrotate.d/app
ls -lh /var/log/app/
~~~

`-v` 输出详细过程，`-f` 强制立即滚动一次，组合起来适合在配置完当场验证；`-d` 是调试模式，上线前先跑一遍，确认没有写错路径再放开。

### 8.1 哪些日志需要自己写规则

系统自带服务一般在安装时就已经放好了规则，自研应用、手工启动的程序、被 systemd 托管的 jar 包则需要自己加。

| 情况 | 是否要自建规则 | 说明 |
| --- | --- | --- |
| 系统自带服务 | 通常不用 | 安装包已在 `/etc/logrotate.d/` 下放好，例如 nginx、mysql |
| 自研应用写固定文件 | 要 | 日志路径和保留天数只有自己知道 |
| systemd 托管的服务 | 要，且必须写 postrotate | 不重载服务就切不动日志文件 |
| 只输出到 journal 的服务 | 不用 | 占用由 journald 的 vacuum 参数控制 |

滚动一次后，目录里的文件构成一条保留链：最新的是 `app.log`，上一份是被改名的 `app.log.1`，再往前是压缩后的 `app.log.2.gz`、`app.log.3.gz`，直到 `rotate` 指定的份数用完，最旧的那份在下次滚动时被删除。看懂这条链，就能在 `df -h` 告警时快速判断是哪个应用没有配好保留策略。

## 9. 小白易错点

| 易错点 | 后果 | 正确做法 |
| --- | --- | --- |
| 用 `tail -f` 长期跟踪会滚动的日志 | 日志切割后命令静默失效，以为服务不写日志 | 长期跟踪用 `tail -F` |
| 管道里 grep 没加 `--line-buffered` | 实时过滤时屏幕长时间不刷新 | 加 `--line-buffered` 按行输出 |
| 直接对几百兆的日志全文件 grep | 扫完整份数据，慢且没必要 | 先用 `tail -n 5000` 截取再过滤 |
| 忘记 `--no-pager` | 输出被 less 接管，脚本里卡住或日志不完整 | 重定向与脚本里一律加 `--no-pager` |
| 以为 journalctl 能看到全部历史日志 | 未开启持久化时重启即丢，查不到关键现场 | 建立 `/var/log/journal` 目录并重启 journald |
| 只盯着应用日志不看系统日志 | OOM、端口占用这类根因完全看不到 | 同时看 `journalctl -u 服务名` 和 `dmesg -T` |
| 用 `-p err` 以为只匹配 err | 实际包含更严重的 crit、alert、emerg | 记住它是“该级别及以上” |
| 时间参数写成模糊表述 | `--since "昨天"` 这类写法不生效 | 用 `10 min ago`、`today` 或完整时间 |
| 磁盘满了才发现日志没管 | 服务写不进日志，故障无法回溯 | 定期 `df -h`，给日志配 logrotate |
| logrotate 没写 `postrotate` | 新日志文件一直是空的，切割不算完成 | 在 postrotate 里 reload 服务 |
| 用 `journalctl --vacuum-time` 清理文本日志 | 文本日志一点没少，空间没释放 | journal 用 vacuum，文本日志交给 logrotate |
| 排障上来就改配置 | 现场被破坏，改完问题还在 | 先按“进程、端口、连通、日志、资源”顺序看 |
| 在日志里贴真实密码或 IP | 敏感信息泄露 | 用 `${DB_PASSWORD}`、`${SERVER_IP}` 这类占位符 |
| 只看最后一行错误就开始改代码 | 忽略前几行才是真正的起因 | 用 `grep -C 3` 看上下文和堆栈起点 |

## 10. 练习清单

| 序号 | 练习内容 | 验收标准 |
| --- | --- | --- |
| 1 | 用 `tail -n 100` 查看 `/var/log/messages`，再用 `head -n 5` 看开头对比 | 能说出为什么排障优先看尾部 |
| 2 | 起一个持续写日志的进程，用 `tail -f` 跟随后手工用 `mv` 改名并新建同名文件 | 观察到 -f 失效、换成 `-F` 后恢复正常 |
| 3 | 用 `grep -c` 统计日志里的 ERROR 行数 | 能给出一个具体数字 |
| 4 | 用 `grep -C 3` 找出某条错误的上下文 | 能指出真正的起因行 |
| 5 | 用 `grep -iE "error\|failed"` 一次匹配多个关键字 | 理解 `-E` 与 `-i` 的组合效果 |
| 6 | 用 `journalctl -u 服务名 -n 50 --no-pager` 查看指定服务日志 | 输出的行都来自该服务 |
| 7 | 用 `journalctl --since "10 min ago" -p err` 查看最近 10 分钟的错误 | 能解释为什么要限定时间 |
| 8 | 开关一次持久化，验证 `journalctl -b -1` 能否查到上次开机日志 | 说出 `/var/log/journal` 的作用 |
| 9 | 用 `df -h` 与 `du -sh /var/log/*` 找出占用最大的日志 | 列出排名前三的日志文件 |
| 10 | 给一个自研日志文件写一份 `/etc/logrotate.d/` 规则并用 `-d` 演练 | 演练输出里出现 rotate 与 postrotate 动作 |
| 11 | 按通用套路完整排查一次“服务访问不了” | 每一步都有命令输出作为证据 |
| 12 | 用 `dmesg -T` 或 `journalctl -k` 找出一次 OOM 记录 | 能指出被杀进程名与内存数值 |

## 12. 本篇总结

1. 日志有两条主线：systemd 的 journal 适合按服务和优先级精确查询，`/var/log` 下的文本日志适合应用自定义输出与脚本处理。
2. 常见日志各司其职：messages 与 syslog 是系统主日志，secure 与 auth.log 记认证，cron 记定时任务，boot.log 记开机，dmesg 记内核，nginx 与 mysql 目录放各自应用的日志。
3. `tail -f` 靠已打开的文件描述符读数据，日志滚动后会失效；`tail -F` 按文件名重新打开，适合生产长期跟踪。
4. 实时过滤要加 `grep --line-buffered`，否则输出被缓冲，看起来像卡住。
5. grep 在日志里的常用组合是 `-C 3` 看上下文、`-v` 排噪音、`-c` 计数、`-i` 忽略大小写、`-E` 多关键字匹配。
6. 排查最近的故障先用 `tail` 截取一段再 grep，比全文件扫描快得多。
7. journalctl 靠 `-u`、`--since`、`--until`、`-p`、`-b`、`-k` 组合过滤，脚本里加 `--no-pager`。
8. journal 默认不持久化，`/var/log/journal` 不存在时重启即丢；建好目录并重启 journald 才能用 `-b -1` 回看上次开机日志。
9. 排障顺序是“服务在不在、端口听没听、本机通不通、远程通不通、应用日志、系统日志、资源与磁盘、配置与权限”，每步都留下证据。
10. 六类高频故障中，OOM 要看 `dmesg` 与 `journalctl -k` 的 out of memory，时间不同步要查 `timedatectl`，权限问题要先看父目录的执行位。
11. logrotate 通过 daily、rotate、compress、missingok、notifempty、create 与 postrotate 组合，解决日志把磁盘写满的问题，其中 postrotate 里的 reload 不可省。
