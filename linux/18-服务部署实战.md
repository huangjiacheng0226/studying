# 十、服务部署实战

> 把一个 jar 包变成“开机自启、崩溃重拉、能通过浏览器访问”的线上服务，中间要过环境、目录、用户、systemd、Nginx、防火墙六道关，本篇按真实顺序走一遍。

## 2. 部署前要准备什么

部署不是“把 jar 传上去跑起来”这么简单。在一台新机器上，要先把四件事定下来，后面每一步才有明确目标：用哪个 JDK 跑、程序放在哪里、用哪个用户跑、监听哪个端口。

| 准备项 | 要定下的内容 | 常见错误 |
| --- | --- | --- |
| 运行环境 | JDK 版本与安装位置、JAVA_HOME 配置 | 机器上只有 JRE，编译期行为与线上不一致 |
| 目录规划 | 程序目录、日志目录、数据目录 | 全部堆在家目录，重装系统或换用户就丢 |
| 运行用户 | 专用非 root 账号及其属组 | 直接用 root 跑，出问题就是整机风险 |
| 端口规划 | 对外端口与内部端口的划分 | 端口随手写，和已有服务冲突 |

### 2.1 安装 JDK 并配置 JAVA_HOME

Java 应用首先要有一个能跑的 JDK。生产机上装 JDK 而不是只装 JRE，一是排查问题时会用到 `jps`、`jstack` 这类诊断工具，二是升级或换版本时不必再补包。

~~~bash
sudo yum install -y java-17-openjdk java-17-openjdk-devel
java -version
readlink -f "$(which java)"
~~~

`java -version` 确认版本，`readlink -f` 顺着 `/usr/bin/java` 这个软链接找到真实的 JDK 目录，例如 `/usr/lib/jvm/java-17-openjdk-17.0.9.0.9-1.el7_9.x86_64`，这个路径就是 JAVA_HOME 要写的值。

配置 JAVA_HOME 推荐放在 `/etc/profile.d/` 下，登录 Shell 会自动加载：

~~~bash
echo 'export JAVA_HOME=/usr/lib/jvm/java-17-openjdk' | sudo tee /etc/profile.d/java.sh
echo 'export PATH=$JAVA_HOME/bin:$PATH' | sudo tee -a /etc/profile.d/java.sh
source /etc/profile.d/java.sh
echo "${JAVA_HOME}"
~~~

这里有一个部署时最常见的坑：`/etc/profile` 只在交互式登录 Shell 里执行，systemd 启动服务时不读它。所以单元文件里不能指望 JAVA_HOME 已经存在，要么在 `[Service]` 段里用 `Environment` 显式声明，要么 `ExecStart` 直接写 java 的绝对路径。

### 2.2 目录与用户规划

把“程序、日志、数据、配置”分开放，是让运维动作变简单的前提：升级只动程序目录，备份只打包数据目录，清理磁盘只看日志目录。

| 用途 | 推荐路径 | 说明 |
| --- | --- | --- |
| 程序目录 | `/usr/local/app` | 放 jar 包、启动脚本、静态资源 |
| 日志目录 | `/var/log/app` | 与系统日志同级，便于 logrotate 统一管理 |
| 数据目录 | `/data/app` | 上传文件、附件、本地缓存，单独挂数据盘 |
| 配置目录 | `/etc/app` | 配置放这里，程序从外部读取，避免打进 jar |
| 备份目录 | `/data/backup` | 与数据目录分开磁盘，避免一起损坏 |

端口也要提前规划并写进文档，尤其是把数据库、Redis 这类内部服务限制在本机监听：

| 服务 | 示例端口 | 监听建议 |
| --- | --- | --- |
| Nginx | 80 与 443 | 监听 0.0.0.0，对外提供访问 |
| Java 应用 | 8080 | 监听 127.0.0.1，只允许 Nginx 反代过来 |
| MySQL | 3306 | 监听 127.0.0.1，除非确实要远程连 |
| Redis | 6379 | 监听 127.0.0.1 并设置密码 |
| SSH | 22 | 监听 0.0.0.0，防火墙按来源限制 |

### 2.3 部署流程一览

从拿到 jar 包到浏览器能打开页面，中间的经历大致如下：

~~~mermaid
flowchart LR
    A[本机打包出 app.jar] --> B[上传到 /usr/local/app]
    B --> C[准备配置文件与数据目录]
    C --> D[systemd 单元托管并设置开机自启]
    D --> E[校验本机 curl 127.0.0.1:8080]
    E --> F[Nginx 反向代理 80 到 8080]
    F --> G[放行防火墙端口]
    G --> H[浏览器访问域名或 IP]
    H --> I[按上线检查清单复核]
~~~

图中的顺序不能颠倒：先让应用本机能访问，再配 Nginx 和防火墙，这样出问题时能立刻判断是应用没起还是入口没通。反过来先配 Nginx，就会在 502 和“端口不通”之间反复摇摆，把时间浪费在猜上。

## 3. 手工启动与 systemd 托管对比

最直接的启动方式是在终端里敲 `java -jar`，三种写法的差别很能说明问题：

~~~bash
cd /usr/local/app
java -jar app.jar
java -jar app.jar > /var/log/app/app.log 2>&1 &
nohup java -jar app.jar > /var/log/app/app.log 2>&1 &
~~~

第一条前台运行，日志直接刷在终端上，好处是启动报错立刻看得见，代价是这个终端一关、SSH 一断，进程就收到挂断信号退出。第二条加 `&` 丢到后台，可终端关闭时的挂断信号依然可能影响它，日志也要自己记得重定向。第三条用 `nohup` 忽略挂断信号，看上去“稳”了，但开机自启、崩溃重启、状态查询、优雅停止全都得自己想办法。

| 维度 | 手工 `java -jar` | systemd 托管 |
| --- | --- | --- |
| SSH 断开 | 前台直接退出，后台也有被挂断风险 | 由 PID 1 拉起，与登录会话无关 |
| 开机自启 | 不支持，重启后必须人工登录再敲一遍 | `enable` 后随系统自动启动 |
| 崩溃重启 | 不会，进程挂了就一直不可用 | `Restart=always` 按间隔自动重拉 |
| 日志 | 要自己重定向，容易漏掉 | 默认进 journal，也能落固定文件 |
| 状态查询 | 只能用 `ps` 翻进程号 | `systemctl status` 一眼看到状态与退出码 |
| 停止方式 | 手工 `kill`，有杀错进程的风险 | `systemctl stop` 精确可控 |
| 环境变量 | 依赖当前 Shell，不可复现 | 单元文件里显式声明，换机器也一致 |
| 依赖顺序 | 无法保证网络、数据库已就绪 | 用 `After`、`Wants` 声明启动顺序 |

结论很直接：手工启动只用来临时验证“jar 本身能不能跑”，正式环境一律交给 systemd。

## 4. 用 systemd 托管 Java 应用

单元文件放在 `/etc/systemd/system/` 下，文件名就是服务名，所以下面这份配置保存为 `/etc/systemd/system/app.service`，之后的服务名就叫 `app`。

~~~conf
[Unit]
Description=Study App Service
After=network.target

[Service]
Type=simple
User=appuser
Group=appuser
WorkingDirectory=/usr/local/app
Environment="JAVA_HOME=/usr/lib/jvm/java-17-openjdk"
Environment="SPRING_PROFILES_ACTIVE=prod"
ExecStart=/usr/lib/jvm/java-17-openjdk/bin/java -jar /usr/local/app/app.jar --server.port=8080
SuccessExitStatus=143
Restart=always
RestartSec=5
StandardOutput=append:/var/log/app/app.log
StandardError=append:/var/log/app/app.log

[Install]
WantedBy=multi-user.target
~~~

三个段落的职责不同：`[Unit]` 描述这个单元是什么、和谁有先后关系，`[Service]` 描述进程怎么跑，`[Install]` 描述开机自启时挂到哪个目标上。

`[Unit]` 段的关键项：

| 配置项 | 含义 | 建议 |
| --- | --- | --- |
| `Description` | 单元的人类可读描述 | 写清这是什么服务，`status` 时会显示 |
| `After` | 明确在哪些单元之后再启动 | 网络服务写 `network.target` |
| `Wants` | 弱依赖，被依赖单元启动失败也不阻塞 | 依赖数据库时写对应单元 |

`[Service]` 段是重点，每一项都对应一个前面提过的问题：

| 配置项 | 解决的问题 | 说明 |
| --- | --- | --- |
| `Type=simple` | 进程模型 | 默认值，`ExecStart` 启动的就是主进程 |
| `User` 与 `Group` | 用哪个身份跑 | 写专用账号，不能省略，否则默认以 root 运行 |
| `WorkingDirectory` | 相对路径的基准 | 程序按相对路径找配置或模板文件时才正确 |
| `Environment` | 环境变量 | 补上 systemd 不读 `/etc/profile` 的空缺 |
| `ExecStart` | 启动命令 | 命令、jar 路径都写绝对路径，不用 `~` 和相对路径 |
| `SuccessExitStatus=143` | 退出码判定 | 收到 SIGTERM 时 JVM 返回 143，声明后重启不会被判为失败 |
| `Restart=always` | 崩溃重拉 | 除主动 stop 外出任何原因退出都重启 |
| `RestartSec=5` | 重启间隔 | 避免启动失败时疯狂重启，把 CPU 和日志刷爆 |
| `StandardOutput` 与 `StandardError` | 输出去向 | `append:` 追加到文件，不写则进 journal |

`Environment` 里的值要用双引号包住，写成 `Environment=JAVA_HOME=/x` 也可以，但含空格时必须加引号。`StandardOutput=append:` 需要 systemd 240 及以上版本，老系统上更稳妥的做法是删掉这两行，让输出进 journal，用 `journalctl -u app -f` 查看。

`[Install]` 段的 `WantedBy=multi-user.target` 表示执行 `systemctl enable app` 时，在 `multi-user.target` 目标下建一个指向本单元的软链接，系统进入多用户模式时顺带把它拉起。少了这一行，`enable` 会报错，服务也不会开机自启。

### 4.1 服务的日常管理命令

~~~bash
sudo systemctl daemon-reload
sudo systemctl enable --now app
sudo systemctl status app --no-pager
sudo systemctl restart app
sudo systemctl stop app
systemctl is-enabled app
systemctl is-active app
journalctl -u app -n 50 --no-pager
journalctl -u app -f
~~~

改动单元文件之后必须先 `daemon-reload`，否则 systemd 用的还是旧配置，这是最容易被忽略的一步。`enable --now` 一步完成“设置开机自启”和“立即启动”。`is-enabled` 返回 enabled 或 disabled，`is-active` 返回 active 或 failed，配上 `--no-pager` 和静默输出很适合写进部署脚本做检查。

看服务日志用 `journalctl -u app`，比翻应用自己写的文件更全，因为它连 systemd 记录的启动失败原因、退出信号都在一起。如果单元文件里配了 `StandardOutput=append:`，两处内容基本一致，选一个顺手的即可。排查启动失败时，`systemctl status app --no-pager` 显示的最近几行日志通常已经给出了答案。

## 5. 非 root 用户与目录权限

应用要用专用账号跑，第一步是把账号建出来并约束住：

~~~bash
sudo useradd --system --shell /sbin/nologin --home-dir /usr/local/app appuser
sudo mkdir -p /usr/local/app /var/log/app /data/app
sudo chown -R appuser:appuser /usr/local/app /var/log/app /data/app
sudo chmod 750 /usr/local/app /var/log/app /data/app
id appuser
ls -ld /usr/local/app /var/log/app /data/app
~~~

`--system` 建的是系统账号，UID 落在 1000 以下；`--shell /sbin/nologin` 禁止交互登录，即使密码泄露也登不进机器；`--home-dir` 把家目录指到程序目录，避免默认建出 `/home/appuser`。`chown -R` 把程序目录、日志目录、数据目录一并交给这个用户，`chmod 750` 保证同组可进、其他人不可进。

为什么不能让应用以 root 身份运行：

| 风险 | 说明 |
| --- | --- |
| 漏洞影响面被放大 | 应用一旦被攻破，攻击者直接拿到 root，可以改系统、装后门、读所有文件 |
| 误操作破坏系统 | 一个写错路径的删除或覆盖命令，可能直接动到系统文件 |
| 进程相互可见 | root 能读取机器上任何进程的内存与文件，横向移动太容易 |
| 审计无法区分 | 所有动作都是 root，日志里分不清是应用干的还是人干的 |
| 掩盖权限问题 | 用 root 能跑通不代表普通用户能跑，上线后才发现权限没配好 |

配置完还要回头检查两件事：jar 文件本身对应用用户可读，日志目录对应用用户可写。最常见的一类启动失败就是“日志目录属主还是 root”，应用刚启动写第一条日志就抛权限异常退出。路径的每一层都要有执行位，用 `namei -l /var/log/app/app.log` 可以逐层看到谁缺了权限。

## 6. Nginx 反向代理与静态资源

Nginx 放在应用前面，作用是统一入口：对外只开 80 与 443，应用端口不直接暴露；静态文件由 Nginx 直接返回，不经过 Java 进程；访问日志与错误日志集中在一处，加 HTTPS 时也只改一处。

### 6.1 反向代理配置

~~~conf
server {
    listen 80;
    server_name ${SERVER_IP};

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
    }
}
~~~

`proxy_pass` 后面的地址就是后端应用，这里写 `127.0.0.1:8080`，意味着后端只允许本机访问，外面必须先过 Nginx。几条 `proxy_set_header` 决定了应用看到什么信息：

| 配置 | 作用 | 不加会怎样 |
| --- | --- | --- |
| `Host $host` | 把浏览器请求的域名传给后端 | 后端拼重定向地址或做多域名判断时拿不到真实域名 |
| `X-Real-IP $remote_addr` | 传客户端真实 IP | 应用日志里全是 127.0.0.1，无法定位来源 |
| `X-Forwarded-For` | 传经过的代理链 | 多级代理下拿不到最初的客户端 IP |
| `X-Forwarded-Proto` | 传原始协议是 http 还是 https | 应用生成链接时可能写错协议 |
| `proxy_connect_timeout` | 连接后端超时 | 后端挂了要等很久才报 502 |
| `proxy_read_timeout` | 读后端响应超时 | 长任务被过早判定超时 |

### 6.2 proxy_pass 末尾斜杠的影响

这是 Nginx 配置里最容易踩的一处：`proxy_pass` 末尾有没有斜杠，转发给后端的路径不同。

| location 写法 | proxy_pass 写法 | 请求 /api/user 实际转发到 |
| --- | --- | --- |
| `location /api/` | `http://127.0.0.1:8080` | `/api/user` |
| `location /api/` | `http://127.0.0.1:8080/` | `/user` |

规则是：`proxy_pass` 带 URI（末尾有斜杠也算带 URI）时，location 匹配到的那段前缀会被替换成这个 URI，所以 `/api` 被换成了 `/`，剩下的 `/user` 接在后面；不带 URI 时，整个原始路径原样转发。配完以后用 `curl -v` 或看 access.log 里的 `$request` 就能验证。

### 6.3 前端静态资源与 try_files

前端打包产物是一堆 html、js、css 文件，只需 Nginx 直接返回，不必让 Java 处理。把文件放到 `/var/www/html` 或 `/usr/local/nginx/html`，`root` 指向它即可。单页应用必须配 `try_files`，否则在前端路由里刷新页面就 404。

~~~conf
server {
    listen 80;
    server_name ${SERVER_IP};
    root /var/www/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8080/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
~~~

`try_files $uri $uri/ /index.html` 的含义是按顺序试：先找 `/var/www/html` 下有没有这个具体文件，再找同名目录，都没有就返回 `index.html`，交给前端路由处理。用户直接访问 `/order/123` 时静态目录里并不存在 `order/123` 这个文件，所以必须靠最后这一步兜底。`root` 指向的目录要保证 Nginx 工作用户可读，否则会看到 403。

### 6.4 检查与生效

改完配置不要直接重启，先让 Nginx 自己校验语法：

~~~bash
sudo nginx -t
sudo systemctl reload nginx
curl -I http://127.0.0.1/
tail -n 20 /var/log/nginx/error.log
~~~

`nginx -t` 输出 syntax is ok 与 test is successful 才继续；`reload` 会平滑加载新配置，已建立的连接不受影响，比 `restart` 更适合生产。最后用 `curl -I` 看响应码，遇到 502 或 403 直接翻 error.log，那里写明了具体原因。

## 7. 防火墙开放端口

本机 `curl` 通了、远程访问不上，最常见的原因就是防火墙没放行。CentOS 系默认用 firewalld，Ubuntu 系默认用 ufw，两者思路相同、命令不同：

| 操作 | firewalld（CentOS/RHEL） | ufw（Ubuntu/Debian） |
| --- | --- | --- |
| 查看状态 | `firewall-cmd --state` | `ufw status verbose` |
| 开放端口 | `sudo firewall-cmd --add-port=8080/tcp` | `sudo ufw allow 8080/tcp` |
| 永久生效 | `sudo firewall-cmd --permanent --add-port=8080/tcp` | `allow` 默认就是持久化的 |
| 让配置生效 | `sudo firewall-cmd --reload` | `sudo ufw reload` |
| 放行已有服务 | `sudo firewall-cmd --permanent --add-service=http` | `sudo ufw allow http` |
| 查看已放行 | `sudo firewall-cmd --list-all` | `sudo ufw status numbered` |
| 撤销放行 | `sudo firewall-cmd --permanent --remove-port=8080/tcp` | `sudo ufw delete allow 8080/tcp` |

两个差别要记牢：firewalld 不带 `--permanent` 的修改只在本次运行有效，reload 或重启就丢，所以放行端口的标准写法是“带 --permanent 加一次，再 reload 一次”；ufw 的 `allow` 默认写进配置，立刻生效也持久保存。

生产环境的放行原则是最小化：只对外开必须提供的端口，比如 80 与 443，8080 这类后端端口不开放，靠 Nginx 反代进来。云服务器上除系统防火墙之外还有一层安全组，两层都放行才通，遇到“本机通、远程不通”时先确认是哪一层拦住的。

## 8. 上线检查清单

部署完成后逐项确认一遍，能拦住绝大多数“看起来好了其实没好”的情况。

| 检查项 | 命令 | 通过标准 |
| --- | --- | --- |
| 进程是否在跑 | `systemctl is-active app` | 输出 active |
| 端口是否监听 | `ss -lntp` | 能看到 8080，属主是应用进程 |
| 本机能否访问 | `curl -I http://127.0.0.1:8080/` | 返回 200 或预期的 302 |
| 远程能否访问 | `curl -I http://${SERVER_IP}/` | 从另一台机器访问也有响应 |
| 日志是否异常 | `tail -n 50 /var/log/app/app.log` | 没有 ERROR 与异常堆栈 |
| 是否开机自启 | `systemctl is-enabled app` | 输出 enabled |
| 磁盘是否充足 | `df -h` | 各分区使用率低于 80% |
| 内存是否充足 | `free -h` | 可用内存与 swap 都还充裕 |
| 时间是否同步 | `timedatectl` | 时间同步状态为 yes |
| Nginx 配置是否有效 | `sudo nginx -t` | test is successful |
| 端口是否已放行 | `sudo firewall-cmd --list-all` | 80 与 443 在放行列表中 |

把这套命令写成一个 `check.sh`，每次上线跑一遍，比每次靠记忆临时敲命令可靠得多；也可以直接接进发布流程，让脚本在检查失败时拒绝继续。

## 9. 常见故障表

| 现象 | 可能原因 | 排查命令 | 常见结论 |
| --- | --- | --- | --- |
| 启动即失败，status 显示 failed | 单元文件路径写错、缺少 JAVA_HOME、jar 权限不足 | `systemctl status app --no-pager`、`journalctl -u app -n 50` | 多为 `ExecStart` 路径或环境变量问题 |
| 端口被占用 | 旧实例没停干净、另一个服务先占了 8080 | `ss -lntp`、`lsof -i:8080` | 停掉旧进程，或改 `--server.port` |
| Java 版本不匹配 | 编译用的 JDK 比运行环境新 | `java -version`、`journalctl -u app -n 50` | 报 UnsupportedClassVersionError，装对齐的 JDK |
| jar 名带版本号写错路径 | `app-1.2.3.jar` 写成了 `app.jar` | `ls -l /usr/local/app/`、`systemctl cat app` | 单元文件里的路径与实际文件名不一致 |
| Nginx 502 | 后端没起、端口不对、超时太短 | `tail -n 50 /var/log/nginx/error.log`、`curl 127.0.0.1:8080` | connect refused 说明后端没监听 |
| Nginx 403 | 静态目录权限不对或目录下没有首页文件 | `ls -ld /var/www/html`、`namei -l /var/www/html/index.html` | 属主或权限不对，或缺少 index.html |
| 防火墙未放行 | 安全组或本机防火墙拦住了 80 | `sudo firewall-cmd --list-all`、`sudo ufw status` | 放行端口后立即恢复 |
| 重启后服务就没了 | 忘了 `enable`，只有运行时启动 | `systemctl is-enabled app` | 输出 disabled，需要 `enable` 补上 |

排查这类问题有一个通用技巧：先看 `systemctl status` 的最后几行，systemd 会直接给出失败原因与退出码，比翻长日志快得多。如果状态是 active 但访问不通，问题就在端口、防火墙或 Nginx，而不在应用本身，此时按第 17 篇的顺序从“端口是否在听”开始查。

## 10. 小白易错点

| 易错点 | 后果 | 正确做法 |
| --- | --- | --- |
| 改完单元文件直接 restart | 用的还是旧配置，改动不生效 | 先 `systemctl daemon-reload` |
| 单元文件里写相对路径 | systemd 的工作目录与预期不同，找不到 jar | `ExecStart` 与 jar 路径都写绝对路径 |
| 指望着 `/etc/profile` 提供 JAVA_HOME | systemd 不读登录脚本，启动即失败 | 在单元文件里用 `Environment` 声明 |
| 用 root 跑应用 | 一旦被攻击就是整机沦陷 | 建专用系统用户并配好属主 |
| 只配了 `Restart=always` 没配 `RestartSec` | 启动失败时疯狂重启，刷爆日志 | 同时设置合理的重启间隔 |
| 忘了 `systemctl enable` | 服务器重启后服务不再运行 | 用 `enable --now` 一次到位 |
| 把 8080 直接开到公网 | 后端端口暴露，绕过 Nginx 的防护 | 只放行 80 与 443，后端绑 127.0.0.1 |
| `proxy_pass` 末尾斜杠随手写 | 请求路径被多切或少切一段，接口 404 | 明确前缀替换规则并实际验证 |
| 单页应用漏配 `try_files` | 前端路由页面刷新即 404 | 用 `try_files $uri $uri/ /index.html` 兜底 |
| 改完 Nginx 直接 restart | 语法错误会让服务起不来，造成中断 | 先 `nginx -t`，再用 `reload` 生效 |
| 手工 `java -jar` 起了就算上线 | SSH 一断服务就停，没人发现 | 一律交给 systemd 托管 |
| 只改系统防火墙没改安全组 | 云上依然访问不通 | 两层放行规则一起检查 |
| 端口与路径规划随手定 | 冲突和混乱在扩容时才暴露 | 部署前把端口与目录写成文档 |

## 13. 本篇总结

1. 部署前要定下四件事：JDK 与 JAVA_HOME、目录规划、专用运行用户、端口规划。
2. systemd 不读 `/etc/profile`，JAVA_HOME 要在单元文件里用 `Environment` 声明，或直接写 java 绝对路径。
3. 程序放 `/usr/local/app`、日志放 `/var/log/app`、数据放 `/data/app`，分开存放让升级、备份、清理互不干扰。
4. 手工 `java -jar` 会在 SSH 断开后退出，且没有自启、没有崩溃重拉、日志难管，正式环境必须交给 systemd。
5. 单元文件由 `[Unit]`、`[Service]`、`[Install]` 三段组成，`WantedBy=multi-user.target` 是 `enable` 生效的前提。
6. `Restart=always` 加 `RestartSec` 实现崩溃自动重拉且不会疯狂重启，`SuccessExitStatus=143` 让优雅停止不被当成失败。
7. 应用要用非 root 专用用户运行，目录属主与全部父目录的执行位都要检查到位。
8. Nginx 反向代理把 80 转发到 127.0.0.1:8080，`proxy_set_header` 让后端拿到真实域名与客户端 IP。
9. `proxy_pass` 末尾带斜杠会替换掉 location 匹配的前缀，带与不带转发路径不同。
10. 单页应用要用 `try_files $uri $uri/ /index.html` 兜底，否则前端路由刷新即 404；改完配置先 `nginx -t` 再 `reload`。
11. 防火墙按最小化原则放行，firewalld 要 `--permanent` 加 `reload`，云服务器还要同时改安全组。
12. 上线后用检查清单复核进程、端口、连通性、日志、自启、磁盘内存与时间同步，把命令写成脚本比靠记忆更可靠。
